## 1. 引言

本文说明第一部云机和它旁边的控制程序怎么摆、怎么调用。编码以此为准。没核实的不写成已有程序。

中小项目，章节按详细设计说明书保留，空话不写。未跑过的不写能用。对照环境不写成运行程序。

## 2. 综合描述

### 2.1 系统目标

人在对话里交代一件事。事由控制程序在云 Android 上做完。卡住或做完，才回到对话。屏幕不是主界面。

### 2.2 系统概述

三块，调用方向固定。

| 程序 | 位置 | 现在 |
|------|------|------|
| 客户端 | 薄壳，形态未定（2026-10-22 删 Rakazo） | 未建。只发交代、只收进度与结果，不含 agent、不带电脑容器。 |
| 控制程序 | 近云机一侧（正式在 Ubuntu 虚拟机；临时在 Mac） | 未接。框架定 Mobilerun。 |
| 云机 | redroid 13 容器（`localhost:5556`，唯一执行目标） | 已实测可操作：装 Portal；L0/L1a/L1b/L2 四层落地（L0 0.3–0.4 s、L1a 1.4–1.7 s、L1b 约 50 ms、L2 16–26 s）。 |

客户端只管收和发。操作发生在控制程序一侧：它调本机（或转发口）adb。人要看屏幕时在云机一侧看，不把画面转到客户端。

### 2.3 运行环境

| 项 | 现状（2026-10-26 起，唯一执行目标） |
|----|-----------------------------------|
| 宿主 | macarm，colima VM（Ubuntu 24.04 / 内核 `6.8.0-117-generic` / aarch64） |
| 内存 | VM 内只稳开一部云机，不并行第二部 |
| 云机镜像 | `redroid/redroid:13.0.0_64only-latest`（arm64；必须 `_64only`，普通版带 32 位 vendor 二进制，init 自检即失败） |

### 3.1 云机

#### 3.1.1 程序特征

#### 3.1.2 功能

提供一部可操作的 Android。装应用、打开应用、接受点击、给出画面，都通过 adb。不在云机里放控制逻辑。

#### 3.1.3 输入 / 输出

| 方向 | 项 | 说明 |
|------|----|------|
| 输入 | adb 连接 | `localhost:5556` → 容器 5555（`QPHONE_TARGET` 默认值；容器起停见 `scripts/redroid-up.sh`） |
| 输入 | `adb install` | 安装指定安装包 |
| 输入 | `adb shell input` | 点击、按键 |
| 输入 | `adb shell am` | 打开应用 |
| 输出 | 命令返回 | 成功或失败原因 |
| 输出 | `screencap` | 当前画面。给人接手时用，不作为主界面 |

#### 3.1.4 数据结构

数据在 **Docker 命名卷 `qphone-data`**（住在 VM 的 ext4 上），抹掉容器数据仍在；要清空 `docker volume rm qphone-data`。

**为什么不用宿主目录**：`-v ~/redroid13-data:/data` 会经 colima 的 virtiofs，`/data` 变成 `type virtiofs`；Android vold 要 ext4 project quota（`FS_IOC_FSGETXATTR`），virtiofs 回 `Inappropriate ioctl for device`，于是 `StorageManager` / `MediaProvider` 一路报存储有问题。实测换成命名卷后 `/data` 是 `type ext4`、错误条数 0。

⚠ 变量名撞车：`REDROID_DATA`（宿主目录，调试用）与 `REDROID_DATA_VOLUME`（默认 `qphone-data`）。**默认走卷**，只有显式给 `REDROID_DATA` 才用宿主目录。

#### 3.1.5 调用关系

被控制程序调用。不被客户端调用。

#### 3.1.6 算法

无自有算法。

#### 3.1.7 限制

一部。VM 内不并行开第二部。端口用 `5556`（`5555` 曾被本机 AVD 占用，虽然 AVD 已删，但端口沿用，避免与「`5555` 其实是模拟器」的旧认知混淆）。**redroid 无 GMS**，依赖 Play 服务的 App 装得上但跑唔起，要另配 OpenGApps。`adb shell input text` 打中文仍 NPE。

#### 3.1.8 载体实测对照（2026-10-26；AVD / 天翼云已排除，只作记录）

| 项 | 天翼云手机 | 本地 AVD `emulator-5554` | 本地 redroid 13 @ `localhost:5556` |
|----|-----------|--------------------------|-----------------------------------|
| `screencap` raw | — | 0.26–0.30 s | **0.11 s** |
| `screencap -p` | 0.61–0.75 s | 0.42–0.66 s | **0.34 s** |
| `uiautomator dump` | 2.25–2.39 s | 2.0–2.2 s | **1.95 s** |
| L1a 快照（`agent-device`） | 1.12–1.14 s | 0.51–0.58 s | 1.12 s（首次）/ **0.42 s**（暖） |
| L0 `am start -W` | 0.12 s（暖） | 0.43 s（冷启）/ 0.14 s（暖） | 0.41 s（冷启）/ **0.04 s**（暖） |
| L2 一单「打开设置」 | 20 步仍未完成（另一单） | 3 步 / 30 s | **2 步 / 16.3 s** |
| 中文 `adb input text` | NPE | NPE | NPE（三边一致） |

结论：本地两种设备都比天翼云快一档，redroid 又比 AVD 快（暖 `am start` 0.04 s vs 0.14 s、raw 截图 0.11 s vs 0.28 s）。`uiautomator dump` 约 2 s、L2 单步 7–8 s 是 Android 自身与模型侧成本，换设备不会变 —— 仍是 L0 优先、L1 常驻、L2 只兜底。

redroid 四个坑（全部实测踩过）：

1. **必须 `_64only` 镜像**。`13.0.0-latest` 带 32 位 vendor 二进制，arm64 VM 上 `init: cannot execv('/vendor/bin/boringssl_self_test32'): Exec format error`，触发 `reboot_on_failure` → 容器 `Exited (129)`、`docker logs` 空白。
2. **modprobe 唔会出 `/dev/binder`**。`modprobe binder_linux devices="binder,hwbinder,vndbinder"` 只令 `/proc/filesystems` 出现 `binder`；要 `mount -t binder binder /dev/binderfs` 才产节点。
3. **节点默认 600**。容器内服务开 `/dev/binder` 得 `Permission denied`，要 `chmod 666`。
4. **节点要 `-v` 绑入容器，唔可以 `--device`**。`--device /dev/binderfs/binder:/dev/binder` 会 `ENXIO`；`-v /dev/binderfs/binder:/dev/binder` 正常。

前置：colima 的 Ubuntu 24.04 minimal 镜像默认 **无** `linux-modules-extra`，要 `apt-get install linux-modules-extra-$(uname -r)`（官方源 130 KB/s，换 `mirrors.aliyun.com` 后约 400 KB/s）。内核 5.18+ 无 `ashmem`，启动参数要 `androidboot.use_memfd=true`。整套动作已封成 `scripts/redroid-up.sh`。

#### 3.1.9 存储（/data）

| 项 | 值 |
|----|-----|
| 后端 | Docker 命名卷 `qphone-data`（VM 内 `/dev/root` ext4） |
| 设备内看到 | `/data` = ext4、18 GB（跟着 VM 盘走），`/storage/emulated` = `/dev/fuse` |
| 持久性 | 删容器不丢；`docker volume rm qphone-data` 才清 |
| 扩容 | 扩 colima VM 盘（`colima stop && colima start --disk <GB>`），设备侧无需改 |
| 反例 | 挂宿主目录 → virtiofs → vold 拿唔到 project id → 系统提示存储有问题（已实测） |

### 3.2 控制程序

#### 3.2.1 程序特征

框架定 **Mobilerun**（MIT，开源 Python 包，不是它的托管云）。它本身就是手机原生 agent：带 `click / long_press / type / swipe / open_app / get_state / take_screenshot / complete` 等手机工具，看屏走无障碍树 + 截图两路。

配套层 `qphone.py`（本仓库）只做 Mobilerun 不管的事：容器起停、开机状态、端口发现、装包、截图。它不做决策，也不调模型。

#### 3.2.2 功能

接收一句交代。在云机上做完，或说出失败原因。做的过程中回报进度。需要人看屏幕时，发出要人，并停在云机一侧。做完发出结果。开机、关机的状态要说得清。

人不用填端口。正式就是本机 `127.0.0.1:5555`；临时由 `qphone.py` 自动发现转发口。

#### 3.2.3 输入 / 输出

| 方向 | 项 | 说明 |
|------|----|------|
| 输入 | 交代 | 来自客户端的一句话，或一个安装包 / 应用名 |
| 输出 | 进度 | 正在做哪一步 |
| 输出 | 要人 | 卡住。人到云机侧看屏幕，不转到客户端 |
| 输出 | 结果 | 做成，或失败原因 |
| 输出 | 状态 | 开、关、能不能操作 |
| 对云机 | adb | 正式 `127.0.0.1:5555`；临时 Mac 转发口 |

对话来回只有这五种。字段名未定，见附录 B1。

#### 3.2.4 数据结构

未建。不编一套假的表。

#### 3.2.5 调用关系

客户端把交代送到控制程序的接口。控制程序只调云机 adb，不把 scrcpy 或屏幕流转到客户端。

**通道（2026-10-22 定并已实现）**：

```
POST /turn   {text: "交代"}
  ← 事件流：progress / needs_human / result / status
```

壳只认这四种事件，不认云机地址、不认 adb。控制程序跑在哪台机、云机是容器还是租用实例，壳都不需要知道。接口层包住 Mobilerun 的调用与结果。

实现：`serve.py`（同仓库，零依赖，默认 `127.0.0.1:8777`）。壳页 `GET /`（`shell.html`）；步骤回放 `GET /replay?id=<轨迹>`（Mobilerun `--save-trajectory step` 出嘅每步截图 + 思考 + 动作）；截图 `GET /traj/<id>/screenshots/<f>`。`GET /health`、`GET /status`、`POST /turn`（SSE）。**已实测两条路径**：① 成功 —— `"打开设置，睇下 Android 版本"` 回 `status → progress×N → result{success:true}`，答案 Android 13；② 失败 —— `"打开图库，睇下有几多张相"` 图库本身无相，agent 8 步用尽，回 `needs_human{reason:"Reached max step count of 8 steps"} → result{success:false}`。云机未连时回 `status{state:"not_ready"} → needs_human → result{success:false}`，唔会挂住。

#### 3.2.6 算法

第一版只要求做透一个场景（见附录 B3）。Mobilerun 直跑用 `mobilerun run "..."`；要看图加 `--vision`，要多步规划加 `--reasoning`。

⚠️ 已踩：`--provider OpenAI` 会按官方模型白名单校验，自定义模型名（Qbridge 的 `workbuddy/deepseek-v4.1-flash`）直接被拒（`Unknown model`）。要走本地 OpenAI 兼容端点，用 `--provider DeepSeek --api_base http://127.0.0.1:7863/v1`。

#### 3.2.7 处理顺序

1. 收到交代。
2. 确认云机可操作。不可操作则返回状态和失败原因，停止。
3. 若交代是安装或打开，先经 adb 做完，返回结果。
4. 若要操作界面，交 Mobilerun 执行，逐步回报进度。
5. 做不下去，发要人，人在云机侧接手。
6. 收到关机交代，关掉这部，返回状态。

#### 3.3.7 实况窗触控（A 方案，2026-10-26 落地）

云机实况窗由「只睇」变成「可以按」：点击＝点云机，拖动＝滑动，另有返回／主页／多任务三个键。

接口（都在 `serve.py`，一律 POST JSON；做完即刻 `screencap` 一帧，令壳马上见到反应）：

| 接口 | body | 动作 |
|------|------|------|
| `POST /device/tap` | `{"x":102,"y":774}` | `adb shell input tap` |
| `POST /device/swipe` | `{"x1":360,"y1":1150,"x2":360,"y2":250,"ms":240}` | `adb shell input swipe`（`ms` 夹在 30–4000） |
| `POST /device/key` | `{"key":"back"}` | `input keyevent`；键表 `back/home/appswitch/menu/enter/del/power/wakeup/sleep` |
| `POST /device/home` | — | 原有，收尾复位 |

坐标换算（壳侧）：画面用 `object-fit:contain`，所以先算真实绘制区再映射，**唔可以**直接用元素宽高：

```
k  = min(boxW/720, boxH/1280)
ox = imgLeft + (boxW - 720k)/2 , oy = imgTop + (boxH - 1280k)/2
x_dev = (clientX - ox)/k , y_dev = (clientY - oy)/k
```

交互判定：位移 <9px 且时长 <600ms → tap；否则 swipe（`ms` 取实际按住时长，夹 80–900）。离线（`liveOff.show`）时唔送输入，避免盲点。

实测（redroid 13，720×1280）：

| 项 | 实测 |
|----|------|
| `input tap` 本身 | 0.030–0.044 s |
| `input swipe` 本身 | 0.27–0.31 s |
| 接口往返（含抓帧） | tap 134–402 ms、swipe 441–452 ms |
| 画面刷新上限 | `screencap` raw 0.11 s → 约 9 fps |

验证链路（真跑过）：抽屉打开 → 浏览器点击映射到设备 (102,774) → 前台变 `com.android.settings/.Settings`；按「返回」→ 回 `com.android.launcher3`，画面同步换帧。

#### 3.3.8 实况直播（方案 B，2026-10-26 落地）

A 方案用「`screencap` 轮询 + 截图」做实况：极限 9 fps、拖拽一跳一跳。B 方案换成 **H.264 视频流 + 浏览器硬解**，触控仍走 `/device/*`。

链路：

```
screenrecord --output-format=h264 -   （设备侧只一路）
        ↓ adb exec-out（Annex-B）
serve.py 切 NAL → [4B len][1B kind][4B ts][payload] → 广播畀所有客户端
        ↓ 同源 HTTP chunked
浏览器 VideoDecoder（AVCC）→ canvas 即时绘制
        ↓ 触摸
/device/tap|swipe|key（frame:false，唔再等截图）
```

关键实现点（每条都系踩过先写）：

| 问题 | 现象 | 做法 |
|------|------|------|
| 设备只允许一路 `screenrecord` | 两个客户端一起连，第二条流冇数据 | 服务端**单路编码 + 队列广播**；进程空闲 8 s 自动收 |
| 中途接入冇关键帧 | `decode: A key frame is required after configure()` | 新客户端（或带 `?fresh=1`）时踢掉当前编码进程重开，保证由 SPS+PPS+IDR 开始；前端收到 key-frame 错误会自动 fresh 重连 |
| Chrome 要 AVCC 唔要 Annex-B | 同上错误 + 「must fill out the description field」 | 自己拼 `avcC`（profile/compat/level + SPS/PPS），`VideoDecoder.configure({description})`；每帧数据用 4 字节长度前缀 |
| 静态画面冇帧 | 新开页面空白 | `screenrecord` 只在画面变时出帧。用 `/screen.png` 画一张底板落 canvas，静止超过 2.5 s 就补一张保鲜 |

实测（redroid 13 / 720×1280 / 6 Mbps）：

| 指标 | A 方案 | **B 方案** |
|------|--------|-----------|
| 刷新率 | 0.9–9 fps（`screencap` 瓶颈） | **21.5 fps**（动画面时实测解码帧数） |
| 发输入 → 画面见到变化 | 340–450 ms（要先抓帧） | **277–294 ms**（其中输入本身 240 ms） |
| 拖拽观感 | 定格跳帧 | 连续 |
| 码流 | — | 约 2 Mbps（动画面）、静止 0 |

限制：`screenrecord` 单次上限 180 s，到期自动重开（前端无感重连）；文字输入仍未解决（`input text` 中文 NPE）。

### 3.4 执行层设计（L0 / L1a / L1b / L2）

#### 3.4.1 为什么要分层

现役只有一个执行通道：截图给模型、模型给坐标。实测（天翼云手机 `127.0.0.1:10532`，Android 13；该载体已停用，数据留作对照）：

| 项 | 实测 |
|----|------|
| `screencap -p`（720×1600 PNG） | 0.61 / 0.75 / 0.61 s |
| 单步总耗时（截图 + 推理） | 2.5–3.5 s |
| 多步任务 | 「记录 20 个俯卧撑入印象笔记」跑满 20 步仍失败（`Reached max step count of 20`） |
| 70 条轨迹工具失败率 | 4 / 191 |

原因不是模型笨，是**每一步都在重新猜界面**，步骤越多误差与耗时累加。故拆成四层，按「能不能确定」从上往下用，把视觉通道的负责步数压到 1–2 步。

#### 3.4.2 L0 确定性命令通道

不给模型、不看屏，直接把交代翻成 adb 命令，做完只做一次结果校验。

| 项 | 内容 |
|----|------|
| 能力 | `am start -W` / `am force-stop` / `pm clear` / `pm list packages` / `settings put` / `svc wifi` / `cmd bluetooth_manager` / `input keyevent` / `input swipe` / `screencap` / `logcat -d` / `dumpsys` / `getprop` |
| 实测 | `am start -W -n com.android.settings/.Settings` = **0.12 s**（已缓存）、0.85 s（冷启） |
| 判定成功 | 命令返回码 + `dumpsys activity activities` 的 `topResumedActivity` 等于目标 Activity |
| 限制 | ① 任何「要理解界面」的操作都做不了 ② **中文输入不可用**：`input text "今日做咗20个俯卧撑"` 直接 `java.lang.NullPointerException: Attempt to get length of null array`（只有 ASCII 能打） |

#### 3.4.3 L1a 无障碍树通道

读系统无障碍树拿语义节点（text / resource-id / bounds / role），按节点动作，不需要猜坐标。

| 项 | 内容 |
|----|------|
| 实现 | 常驻 instrumentation helper（`agent-device` CLI v0.21.31 实测可用；亦可自建） |
| 实测 | 裸 `uiautomator dump` **2.25–2.39 s**（每次都起 instrumentation）；常驻 helper 快照 **1.12–1.14 s**，内容无变时 0.4 s 直接返回「unchanged」 |
| 中文输入 | 需机内 IME：`agent-device open --test-ime` + `fill`（实测中文标题写入成功） |
| 限制一 | **WebView 内容会延迟出现**：无障碍树由 Chromium 侧在 a11y 服务 attach 后惰性构建。实测印象笔记模板页 uiautomator 能读到 494 节点（其中 257 个 TextView 在 WebView 内）—— 不是读不到，是**首次访问常为空或滞后**，需重试一次 |
| 限制二 | **富文本编辑器读回不可靠**：`en-note` 的 contenteditable 节点只报「可编辑、无文本值」，填充后读回验证失败（实测 `Android fill verification failed`） |
| 限制三 | 失败动作会令整帧 `@ref` 失效（实测 `Ref @e4 belongs to an expired ref frame`），必须重新快照，每次失败多 1.1 s |

#### 3.4.4 L1b WebView CDP 通道（有条件）

Android WebView 支持 Chrome DevTools 协议，但**只有宿主 App 调用过 `WebView.setWebContentsDebuggingEnabled(true)` 才会开 abstract socket**。

| 项 | 内容 |
|----|------|
| 接入 | `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>` → 走 CDP |
| 能力 | `DOM.querySelector` / `Runtime.evaluate` / `Input.insertText`（中文直接注入，**绕过 IME**）/ `Page.captureScreenshot` |
| 速度 | 与 PC 同级：PC 实测读全页 DOM 22 节点 **2.5 ms**；同机对比 uiautomator 2300 ms，差三个数量级 |
| 实测限制 | 第三方 App 默认唔开会话：印象笔记运行中 `/proc/net/unix` 只见 `WebViewZygoteInit`，**无 `*_devtools_remote` socket** → 外人接唔到 |
| 可用范围 | 我方可控的 WebView（Portal APK、自家壳、自研 App）一定可用；第三方 App 待其自身开启；机内 agent（R2）可在运行时打开 |

#### 3.4.5 L2 视觉通道

Mobilerun：截图 + 多模态模型找控件，输出 `click{index}` / `type` / `swipe` 等。**只做兜底**：L0/L1 都不认识界面时才用，步数上限 20。

#### 3.4.6 路由与降级规则

| 交代类型 | 起点 | 升级条件 |
|----------|------|----------|
| 已在 L0 能力表内（开关 App、改设置、装包、按键、截图） | L0 | 命令失败或前台 Activity 不符 → L1a |
| 原生控件界面（设置、系统 App、多数工具类） | L1a | 快照找不到目标节点，或两轮未达成 → L1b（若为 WebView）或 L2 |
| WebView 且我方可控 | L1b | CDP 无 socket / 找不到选择器 → L2 |
| WebView 但第三方 App | L1a 读外壳 + IME 输入 | 正文类富文本 → L2 |
| 游戏、自绘、Canvas | L2 | — |

同一单任务每层只试一次，最多一轮降级；L2 仍失败则出「要人」，附最后一张截图与已执行动作列表。

#### 3.4.7 预算与失败处理

| 项 | 值 |
|----|----|
| L0 单步超时 | 10 s |
| L1 单次快照超时 | 8 s；同一界面连续两次快照无变化视为卡住 |
| L2 步数上限 | 20（沿用现设置） |
| 整单预算 | L0 + L1 合计 ≤ 30 s，超出即降 L2 |
| 失败归因 | 每条历史记录写明「失败在哪一层、最后动作、最后截图」，供人工复核 |

`~/目标/积累/ctyun/cloudphone-ops-agent-prd.md` 是**云手机运维/客服**场景（投诉 → 分配云机 → AI 排查 → 报告），本设计只复用其 §4 的 ADB 能力矩阵作为 L0 目录，不沿用其产品形态。

#### 3.4.9 落地实现（`layers.py`，已跑通）

代码在 `layers.py`，`serve.py` 嘅 `run_agent()` 第一步就调 `layers.route(text)`；命中就唔开 Mobilerun。

**逐层判定规则**（每层自己决定「接唔接呢句」，接唔到就返回 `None`，交下一层）

| 层 | 判定依据 | 动作 | 断言 |
|----|----------|------|------|
| L0 | 正则命中 20 类能力（打开 app / 回桌面 / 关 app / 清数据 / 卸载 / 音量 / 亮度 / Wi-Fi / 蓝牙 / 飞行模式 / 截图 / 装包 / 列包 / 属性 / 开网址 / 点坐标 / 滑动 / ASCII 输入 / 查前台 / 按键） | `am start -W -n`、`input keyevent`、`settings put`、`svc wifi`… | `topResumedActivity` 变到目标包、`settings get` 读回一致 |
| L1a | 动词（点击/点开/按/选/打开/进入）+ 目标词 | `agent-device snapshot -i` → 按 label/identifier 精确→包含→去空格模糊 → `input tap` 控件中心 | 前台包变咗 **或** 快照 hash 变咗 |
| L1b | 存在 `@webview_devtools_remote_*` socket（App 自己开咗 `setWebContentsDebuggingEnabled`） | `adb forward` → `/json` 找 page → WebSocket `Runtime.evaluate` 找文字元素 `.click()` | JS 返回值 `ok:true` |
| L2 | 上面全 miss | `mobilerun run`（视觉 + LLM） | Mobilerun 自己判 |

**实测（redroid 13 / 720×1280）**

| 层 | 用例 | 耗时 |
|----|------|------|
| L0 | 打开设置 | **316–399 ms** |
| L0 | 回桌面 / 查前台 | 30 ms / 27 ms |
| L0 | 调亮度 120 | 89 ms |
| L1a | 快照（冷 / 暖） | 0.41 s / **0.12 s** |
| L1a | 点「网络和互联网」（设置页，英文 label） | **1.39–1.69 s**（含点击后复核快照） |
| L1b | 网页点按钮 / 填输入框 | **41–56 ms** / 32 ms |
| L2 | 一单多步任务 | 16–25 s |

> L1b 嘅 41 ms 系 CDP 往返本身；要有 socket 先成立。系统 WebView shell 有，Portal 冇。

**L1a 嘅两个现实约束**

1. a11y 树系**设备语言**（本机 en-US），用户讲中文 → 内置 `I18N` 映射常见项（网络和互联网→Network & internet 等）；映射唔到就 miss，交 L2，**唔硬猜**。
2. 命中要求节点 `visibleToUser` 且非系统栏；滚动区下面未展开嘅项仍然搵唔到（同 L1a 盲点一致）。

#### 3.4.12 三层覆盖与「为什么又落 L2」

L0 与 L1a 系规则命中，**冇命中就系冇命中**，唔会硬猜。为免「乜都落 L2」，2026-10-26 补咗：

| 改动 | 之前 | 之后 |
|------|------|------|
| 打开 app 讲法 | 只认 `打开/开/启动/开启/进入` | 加 `去/用/睇/看/launch`，并吃 `个 / 一下` |
| 打开未装 app | 照 `am start` 等 5 s 超时 | 先查包表，未安装即回「确定结论」（`final`，唔再烧 L1/L2） |
| 「查有冇装 X」 | 冇呢个能力（会落到 L2 翻设置） | L0 直接查包表：`pm list packages <pkg>`，有/冇即答（`去设置查找有无闹钟app` → 0 ms 答「有装：com.android.deskclock」） |
| L1a 动词 | `点击/点/按/选/打开/进入` | 加 `查找/找/搜/搜索/查看/睇/看/填/输入` |
| 落 L2 时 | 只写「未命中」 | 逐层写明原因，例如「L0 能力表冇呢句；L1a 冇「动作+目标」可对号入座；L1b 冇 WebView 调试 socket」 |

另加常见第三方 app 别名表（印象笔记 / 微信 / 抖音 / 小红书 …），令「有无装 X」「打开 X」对得上包名；表外又唔喺机上嘅名，一律当唔识，唔乱猜。

#### 3.4.13 触发条件公示（`GET /layers`）

「点解走呢层」唔靠估，接口直接列条件；`last_attempts` 回报上一单每层结果。

| 层 | 触发条件（全部要满足） | 执行 | 断言 |
|----|------------------------|------|------|
| L0 | 正则命中能力表（打开/关/查有无装/下载安装查重/音量/亮度/开关/截图/点坐标/滑动/ASCII/查前台） | `adb shell` 直连 | `topResumedActivity` / `settings get` / `pm list` 读回 |
| L1a | ① 正则「动词 + 1~12 字目标」② 动词 ∈ {点击,点开,点,按下,按,选择,选,打开,进入,查找,找,搜,搜索,查看,睇,看,填,输入,tap,click} | `agent-device snapshot -i` → 命中控件 → `input tap` 中心 | 前台包变 或 快照 hash 变 |
| L1b | ① 同上「动词+目标」② `/proc/net/unix` 有 **前台 App** 嘅 `@webview_devtools_remote_<pid>` | `adb forward` → `/json` → WebSocket `Runtime.evaluate` | JS 返回 `ok:true` |
| L2 | 上面全 miss | `mobilerun run` | Mobilerun 自判 |

两条容易踩错嘅点，已修：

1. **L1b 拣错 socket**：机身可能同时有几个 WebView 调试 socket（应用宝、WebView shell 各自一个）。原本取第一个，会点错 App。改为先 `pidof <前台包>`，只认尾巴 pid 对得上嘅 socket。
2. **包名别名写错**：印象笔记国行包名系 `com.yinxiang`（唔系 `com.evernote`），应用宝系 `com.tencent.android.qqdownloader`。别名错会令「有无装 X」误答「未安装」——所以搵唔到别名时改为列出机上第三方 app，唔好一口咬定冇装。

另加「去<app>做X」前缀：先开 App，再把剩余意图跑第二轮（例如「去应用宝下载快手」= 开应用宝 + 再判「下载快手」）。

#### 3.4.14 命中强调与用量统计

**命中强调**：某层判定成功时，该组件闪内嵌 2px 实黄（复用 `amberblink` 参数：`rgba(251,191,36,.45) → 1 → .45`，1.1 s，2 次），闪完停喺绿框（`.ok`）+ 毫秒数。

坑：`paint()` 每次重画会清掉节点 className，靠 class 挂动画会被抹。故用 Web Animations API（`nd.animate([...])`）挂喺元素上，另加 `PULSED` 表保证**一单每层只闪一次**（`layerReset()` 清表），实测脉冲 0.6 s 起、2.07 s 止，正好 2×1100 ms。

**用量统计**：服务端 `LAYER_STATS = {L0,L1a,L1b,L2}` 会话级累计，每单短路到一层就 +1（L2 兜底亦计），`result` 事件带 `layer_stats` + `layer_total`。

壳喺结果卡下方画一行占比：每层一根 44×4 px 细条 + `百分比 · 单数`，本单命中那层条用 `--ok`，零值降到 42% 透明。

> 口径：**按单计**，唔系按调用次数——一单只会落到一层（短路降级），所以四层百分比加起来 100%（用最大余数法取整，唔会出现 63%+38%=101%）。

#### 3.4.15 人工接管后续跑

以前 L2 一失败就整单收工（例如撞到登录墙、验证码）。现在改成**可暂停可续跑**：

| 环节 | 行为 |
|------|------|
| 第一次失败 | 服务端记低 `RUN = {text, used, of, round, active}`，推 `need_hand`（原因 / 已用步数 / 第几次机会），`result` 带 `resumable: true` |
| 壳 | 弹「云机 · 等你接手」卡 + 输入框（可写你处理咗咩）+ 「我已处理好，继续」按钮 |
| 用户点击 | `POST /turn/resume {note}` → 由**当前画面**续跑，prompt 带「用户已接管处理：…／唔好重做已完成步骤」 |
| 步数 | 累计唔重置：续跑用剩余步数（`of - used`），壳显示累加后嘅 `STEP 10 / 20` |
| 上限 | 最多 `QPHONE_RESUME`（默认 3）次；用尽或步数耗尽 → 正常失败收工 |
| 同卡 | 续跑用 `resume_started` 事件（唔系 `task_started`），复用原来嗰张任务卡，唔会开新卡 |

坑：`step` 事件由 Mobilerun 自己数，续跑会由 1 重新数，所以壳要 `STEP_BASE` 加返前面用咗嘅步数。
