>
> 日期：2026-10-27

## 1. 综合描述

### 1.1 系统目标

跑通以下几个通用场景，达到「一部 24×7 的云 Android 手机：人讲一句，云机做完，回一句有证据的结果」。

| 编号 | 场景 | 判定方式（用 adb 核对，不靠模型自述） |
|---|---|---|
| **G1** | 打开音乐 App，进入目标歌单，找到指定歌曲并开始播放 | `dumpsys media_session` 显示 `state = PLAYING`，并且 `title` 与歌名相符 |
| **G2** | 打开只有移动端的 App，发布一条带图片的动态（Soul 只是一个例子） | 回到「我的 → 动态」列表后，snapshot 能取到本次发布的文字，并且该条带图 |
| **G3** | 打开教育类 App，完成做题或考试 | 结果页出现得分或「已交卷」，或者列表状态从「未做」变成「已完成」 |

### 1.2 系统概述

系统由三部分组成，调用方向固定：人 → 客户端 → 控制程序 → 云机。屏幕不是主界面，只有需要时人才去看云机的画面。

| 程序 | 位置 | 现状 |
|------|------|------|
| 客户端 | 薄壳，形态尚未确定（2026-10-22 已删掉 Rakazo 方案） | 未建。它只负责发出任务、接收进度和结果，内部不包含 agent，也不带电脑容器。 |
| 控制程序 | 部署在靠近云机的一侧（正式环境放 Ubuntu 虚拟机，临时放在 Mac 上） | 尚未接通，框架定为 Mobilerun。 |
| 云机 | redroid 13 容器（`localhost:5556`，目前唯一的执行目标） | 已实测可以操作：Portal 已装，L0/L1a/L1b/L2 四层已落地（L0 0.3–0.4 s、L1a 1.4–1.7 s、L1b 约 50 ms、L2 16–26 s）。 |

客户端只负责收和发。真正的操作发生在控制程序一侧：它调用本机 adb（或通过转发口）下发命令。人需要看屏幕时，直接看云机一侧的画面，系统不会把画面转发到客户端。

### 1.3 运行环境

| 项目 | 现状（2026-10-26 起，这是目前唯一的执行目标） |
|----|-----------------------------------|
| 宿主 | macarm，colima 虚拟机（Ubuntu 24.04 / 内核 `6.8.0-117-generic` / aarch64） |
| 内存 | 虚拟机内只能稳定开一部云机，不能并行开第二部 |
| 云机镜像 | `redroid/redroid:13.0.0_64only-latest`（arm64；必须用 `_64only` 版本，普通版本带 32 位 vendor 二进制，init 自检就会失败） |
| 云机系统 | Android 13 / SDK 33 / **arm64-v8a** / 型号 `redroid13_arm64_only` |
| 云机入口 | `localhost:5556` 转发到容器内 5555；启动和停止用 `scripts/redroid-up.sh`（`up` / `down` / `status`） |
| 控制程序 | Mac 本机运行 `python3 serve.py`（`127.0.0.1:8777`），`QPHONE_TARGET` 的默认值就是 `localhost:5556` |
| 客户端 | 薄壳，形态尚未确定。候选方案：Telegram、Hermes 桌面顶栏，或者自己写一个 Tauri/Electron 薄壳 |

### 1.4 程序结构说明

| 最终程序 | 种类 | 谁调用它 |
|----------|------|----------|
| 客户端薄壳 | 未建，形态尚未确定 | 人 |
| 控制程序 | Mobilerun（Python 包，跑在控制机上）加上 `qphone.py` 配套层 | 接收客户端发来的任务，调用云机的 adb |
| 路由器 | `serve.py` 内的 `classify()` 和 `layers.route()`（2026-10-26 落地） | 把一句话分派给对话、L0、L1a、L1b 或 L2 |
| L1 工具 | `agent-device` 命令行工具（MIT 许可，常驻 android-helper） | 路由器在 L1 阶段调用，也可以换成自建的 helper |
| Portal APK | 装在云机上的 Android 应用 | 被 Mobilerun 调用，提供无障碍树和点击能力 |
| redroid 13 容器 | 现成镜像（`localhost:5556`） | 控制程序通过 adb 操作它 |

### 1.5 源程序及编译链接组装说明

第一部云机不在这台机器上编译，而是直接使用官方镜像（或租用实例）运行。

这台虚拟机本身可以编译，A9 就是在这里编译出来的，编译产物会保留。不过 A9 只用作对照，不是这一部的组装方式。

控制程序的源码在 `~/projects/qphone-bot-dev`（名字暂定），入口是 `qphone.py`：一个不依赖第三方库的 adb 薄壳，只负责容器起停、开机状态、端口发现、装包和截图，不做决策。Mobilerun 通过 `uv tool install mobilerun` 安装，agent 的决策由它完成。仓库名和许可证见附录 B4。

| 三类边界 | 内容 |
|----------|------|
| **用户看见的** | 用户看到的是对话，不是远程桌面；只有卡住时才把屏幕递过来；一句话就能关机，状态也说得清楚 |
| **第一版要跑通的** | 一部云手机，不需要用户手填端口；借用现成项目完成装包和点一步操作；换一台干净机器按文档能复现 |
| **不在这张图里承诺的** | 集群、移动端、Windows 都不在范围内；容器方案二选一已经定死；系统服务这周就编进镜像 |

**每一层各自有一条通道**（四条通道各管各的，互不依赖）

| 层 | 自有通道 | 具体命令 |
|----|----------|------|
| L0 | **adbd**（系统命令，不需要安装任何东西） | `am start` / `am force-stop` / `pm uninstall` / `pm clear` / `pm list packages` / `settings put` / `input` |
| L1a | **snapshothelper**（机内无障碍 helper `com.callstack.agentdevice.snapshothelper` v0.21.31） | `adbd` 让它输出无障碍树，并派发点击 |
| L1b | **WebView 调试 socket**（页面本身，不需要额外组件） | `@webview_devtools_remote_<pid>` → `adb forward` → CDP `Runtime.evaluate` / `Input.insertText` |
| L2 | **Portal**（`com.mobilerun.portal`） | `MobilerunAccessibilityService` 读树，加上 `MobilerunContentProvider` 通过无障碍接口 `dispatchGesture` 派发手势 |

推论（用于排查）：四条通道彼此独立——`snapshothelper` 挂掉只会让 L1a 失效；WebView socket 不存在（App 没有开调试）只会让 L1b 失效；Portal 挂掉只会让 L2 失效；L0 依赖 adbd，即使前三条全部挂掉也不受影响。

### 2.1 云机

#### 2.1.1 程序特征

云机是一个现成的容器，镜像为 `redroid/redroid:13.0.0_64only-latest`（arm64），它不是本项目编译出来的可执行文件。
唯一需要连的地址是 `localhost:5556`，它对应容器内的 5555 端口，由 `scripts/redroid-up.sh` 负责启动和停止。
已经排除的载体（2026-10-26）：本机 AVD 模拟器（已删除）、天翼云手机（不再使用）。

#### 2.1.2 功能

云机提供一部可以操作的 Android 设备。安装应用、打开应用、接受点击、输出画面，全部通过 adb 完成。控制逻辑不放在云机里。

#### 2.1.3 输入 / 输出

| 方向 | 项 | 说明 |
|------|----|------|
| 输入 | adb 连接 | `localhost:5556` → 容器 5555（`QPHONE_TARGET` 默认值；容器起停见 `scripts/redroid-up.sh`） |
| 输入 | `adb install` | 安装指定的安装包 |
| 输入 | `adb shell input` | 执行点击和按键 |
| 输入 | `adb shell am` | 启动应用 |
| 输出 | 命令返回 | 返回成功，或者返回失败原因 |
| 输出 | `screencap` | 当前画面，只在需要人接手时使用，不作为主界面 |

云机不向客户端提供屏幕画面，也不提供控制入口。

#### 2.1.4 数据结构

数据存放在 **Docker 命名卷 `qphone-data`** 里（该卷位于 VM 的 ext4 文件系统上），即使删掉容器，数据依然存在；要清空数据则执行 `docker volume rm qphone-data`。

**为什么不用宿主目录**：如果改成 `-v ~/redroid13-data:/data` 挂载宿主目录，读写就要经过 colima 的 virtiofs，`/data` 会变成 `type virtiofs`。Android 的 vold 需要 ext4 的 project quota（`FS_IOC_FSGETXATTR`），而 virtiofs 会返回 `Inappropriate ioctl for device`，于是 `StorageManager` 和 `MediaProvider` 会一路报存储有问题。实测换成命名卷之后，`/data` 是 `type ext4`，错误条数为 0。

⚠ 两个变量名容易混淆：`REDROID_DATA`（宿主目录，调试用）与 `REDROID_DATA_VOLUME`（默认为 `qphone-data`）。**默认走命名卷**，只有显式传入 `REDROID_DATA` 才会使用宿主目录。

#### 2.1.5 调用关系

云机由控制程序调用，客户端不会直接调用它。

#### 2.1.6 算法

云机没有自己的算法。

#### 2.1.7 限制

只开一部。同一个 VM 内不会并行启动第二部。端口固定用 `5556`（`5555` 曾经被本机 AVD 占用；虽然 AVD 已经删除，仍然沿用 `5556`，以免和「`5555` 其实是模拟器」的旧认知混淆）。**redroid 没有 GMS**，依赖 Play 服务的 App 虽然装得上，但运行不起来，需要另外配置 OpenGApps。`adb shell input text` 输入中文仍然会触发 NPE。

#### 2.1.8 载体实测对照（历史记录；AVD / 天翼云已排除）

| 项 | 天翼云手机 | 本地 AVD | 本地 redroid 13 |
|---|---|---|---|
| screencap -p | 0.61–0.75 s | 0.42–0.66 s | **0.34 s** |
| uiautomator dump | 2.25–2.39 s | 2.0–2.2 s | 1.95 s |
| L1a 快照（冷/暖） | 1.12 s | 0.51–0.58 s | 1.12 / **0.42 s** |
| L0 `am start -W` | 0.12 s（暖） | 0.43 / 0.14 s | 0.41 / **0.04 s** |
| L2 一单「打开设置」 | 20 步未完成 | 3 步 / 30 s | **2 步 / 16.3 s** |

结论：redroid 最快；`uiautomator dump` 约 2 s、L2 单步 7–8 s 是 Android 和模型侧的成本，换设备也不会改变——所以 L0 优先、L1 常驻、L2 只做兜底。

redroid 有四个坑（均为实测）：① 必须使用 `_64only` 镜像（普通版带 32 位 vendor 二进制，会报 `Exec format error`，容器以 Exited 129 退出）；② `modprobe binder_linux` 只会让 `/proc/filesystems` 里出现 binder，还需要执行 `mount -t binder binder /dev/binderfs` 才会生成设备节点；③ 节点默认权限是 600，容器内要把它改成 `chmod 666`；④ 绑定节点要用 `-v`，用 `--device` 会返回 ENXIO。前置条件是：VM 要安装 `linux-modules-extra`，启动参数要加上 `androidboot.use_memfd=true`（5.18 以上版本没有 ashmem）。整套流程已经封装成 `scripts/redroid-up.sh`。

#### 2.1.9 存储（/data）

| 项 | 值 |
|----|-----|
| 后端 | Docker 命名卷 `qphone-data`（VM 内 `/dev/root` ext4） |
| 设备内看到 | `/data` = ext4、18 GB（跟着 VM 盘走），`/storage/emulated` = `/dev/fuse` |
| 持久性 | 删除容器不会丢；只有执行 `docker volume rm qphone-data` 才会清 |
| 扩容 | 扩容 colima VM 的磁盘（`colima stop && colima start --disk <GB>`），设备侧不需要改动 |
| 反例 | 挂载宿主目录 → virtiofs → vold 拿不到 project id → 系统提示存储有问题（已实测） |

### 2.2 控制程序

#### 2.2.1 程序特征

框架确定为 **Mobilerun**（MIT 许可的开源 Python 包，不是它提供的托管云服务）。它本身就是面向手机的原生 agent，自带 `click / long_press / type / swipe / open_app / get_state / take_screenshot / complete` 等手机操作工具，观察屏幕有两条途径：无障碍树和截图。

配套的 `qphone.py`（本仓库）只负责 Mobilerun 不管的事情：容器起停、开机状态、端口发现、装包和截图。它不做决策，也不调用模型。

#### 2.2.2 功能

控制程序接收用户的一句话交代，然后在云机上把这件事做完，或者说明失败原因。执行过程中要回报进度；需要人看屏幕时，发出「要人」信号并停在云机一侧，不把画面转到客户端；做完后发出结果。开机和关机的状态也要说得清楚。

用户不需要填写端口：正式环境固定用本机的 `127.0.0.1:5555`，临时环境由 `qphone.py` 自动发现转发端口。

#### 2.2.3 输入 / 输出

| 方向 | 项 | 说明 |
|------|----|------|
| 输入 | 交代 | 来自客户端的一句话，或者一个安装包 / 应用名 |
| 输出 | 进度 | 当前正在做哪一步 |
| 输出 | 要人 | 流程卡住时，由人到云机一侧看屏幕，画面不转到客户端 |
| 输出 | 结果 | 任务做成，或者失败原因 |
| 输出 | 状态 | 开机、关机，以及当前能不能操作 |
| 对云机 | adb | 正式环境用 `127.0.0.1:5555`，临时环境用 Mac 上的转发端口 |

客户端与控制程序之间的往来只有这五种。字段名尚未确定，见附录 B1。

#### 2.2.4 数据结构

尚未建立。不编造一套虚假的表结构。

#### 2.2.5 调用关系

客户端把交代发送到控制程序的接口。控制程序只调用云机的 adb，不会把 scrcpy 或屏幕流转发给客户端。

**通道（2026-10-22 确定并已实现）**：

```
POST /turn   {text: "交代"}
  ← 事件流：progress / needs_human / result / status
```

壳只识别这四种事件，既不认云机地址，也不认 adb。控制程序运行在哪台机器上、云机是容器还是租用实例，壳都不需要知道。接口层负责封装 Mobilerun 的调用和结果。

实现位于 `serve.py`（同仓库，零依赖，默认监听 `127.0.0.1:8777`）。壳页通过 `GET /` 获取（文件为 `shell.html`）；步骤回放通过 `GET /replay?id=<轨迹>` 获取（内容是 Mobilerun 用 `--save-trajectory step` 保存下来的每步截图、思考过程和动作）；截图通过 `GET /traj/<id>/screenshots/<f>` 获取。另外还有 `GET /health`、`GET /status` 和 `POST /turn`（SSE）。**已经实测两条路径**：① 成功 —— `"打开设置，睇下 Android 版本"` 依次返回 `status → progress×N → result{success:true}`，答案是 Android 13；② 失败 —— `"打开图库，睇下有几多张相"` 时图库本身没有照片，agent 把 8 步用尽，返回 `needs_human{reason:"Reached max step count of 8 steps"} → result{success:false}`。云机没有连接时，会依次返回 `status{state:"not_ready"} → needs_human → result{success:false}`，不会一直卡住。

#### 2.2.6 算法

第一版只要求把一个场景做透（见附录 B3）。直接运行 Mobilerun 用 `mobilerun run "..."`；需要看图就加 `--vision`，需要多步规划就加 `--reasoning`。

⚠️ 已经踩过的坑：`--provider OpenAI` 会按官方模型白名单做校验，自定义的模型名（Qbridge 的 `workbuddy/deepseek-v4.1-flash`）会被直接拒绝，报 `Unknown model`。如果要走本地的 OpenAI 兼容端点，需要改用 `--provider DeepSeek --api_base http://127.0.0.1:7863/v1`。

#### 2.2.7 处理顺序

1. 收到用户交代。
2. 确认云机可以操作。如果不能操作，就返回当前状态和失败原因，然后结束。
3. 如果交代的是安装或者打开应用，先通过 adb 做完，再返回结果。
4. 如果需要操作界面，就交给 Mobilerun 执行，并逐步回报进度。
5. 如果做不下去，就发出「要人」信号，由人在云机一侧接手。
6. 如果收到关机交代，就关掉这一部云机，并返回状态。

### 2.3 客户端

#### 2.3.1 程序特征

客户端目前规划为一个「薄壳」，尚未开始建设。它只做三件事：接收用户发来的一句交代，显示进度，显示结果（其中包括需要人来处理的情况）。它内部不包含 agent，不携带「电脑」容器，也不依赖 docker。

2026-10-22，原本打算直接采用现成的 Rakazo 桌面端，该方案**已经完整删除**，容器、镜像、数据卷和源码目录一并清理干净。理由是：Rakazo 自带 agent 和「电脑」容器，这与「客户端只是一个壳」的定位冲突。两层 agent 叠加在一起，会造成 token 重复消耗、步数被放大，而且出错时分不清是哪一层出的问题。同一天也否决了 dsh 桌面端，因为它同样属于自带 agent 的 harness（一套自带 agent 的运行框架），而不是壳。

候选形态有两种，目前尚未决定，见附录 B7：① 先用 Telegram 或 Hermes 桌面端顶上，零开发成本；② 自己写一个薄壳（Tauri 或 Electron），可以打包三个平台。

#### 2.3.2 功能

客户端给用户提供一个对话入口。用户在这里发出交代，客户端显示进度、需要人处理的事项、结果和状态。客户端不打开云手机画面，也不在客户端里点击云手机。

#### 2.3.3 输入 / 输出

| 输出 | 转发给控制程序的交代 |

| 输出 | 显示给用户 |

壳只调用 `POST /turn` 和事件流这两个接口。它不连接 adb，也不关心云手机是从哪里来的。

#### 2.3.4 数据结构

#### 2.3.5 调用关系

用户调用壳，壳只调用控制程序的接口。壳既不会直接调用云手机的 adb，也不会访问 `127.0.0.1:5555`，因为这个地址不在壳这一侧。

#### 2.3.6 算法

无。

#### 2.3.7 实况窗触控

在实况窗里，点击就是对云手机执行点按，拖动就是执行滑动，另外还提供三个系统按键。接口采用 `POST` JSON，每次操作完成之后立即抓一帧，让壳马上看到反应：`/device/tap {x,y}`、`/device/swipe {x1,y1,x2,y2,ms}`、`/device/key {key}`（back/home/appswitch/menu/enter/del/power/wakeup/sleep）、`/device/home`。

坐标换算要注意画面使用了 `object-fit:contain`，因此不能直接用元素的宽高来计算：

```
k  = min(boxW/720, boxH/1280)
ox = imgLeft + (boxW - 720k)/2 ,  oy = imgTop + (boxH - 1280k)/2
x_dev = (clientX - ox)/k ,        y_dev = (clientY - oy)/k
```

判定规则是：位移小于 9 px 并且按住时间小于 600 ms 时判定为 tap，否则判定为 swipe（ms 取按住时长，并夹在 80–900 之间）。云手机离线时不发送输入。实测数据：`input tap` 本身耗时 30–44 ms，`swipe` 耗时 0.27–0.31 s；接口往返（包含抓帧）时，tap 为 134–402 ms，swipe 为 441–452 ms。

#### 2.3.8 实况直播（H.264）

链路是这样的：`screenrecord --output-format=h264 -` → `adb exec-out` → 由 serve 切分 NAL 并广播（`[4B len][1B kind][4B ts][payload]`）→ 浏览器端的 `VideoDecoder` 硬解 → 绘制到 canvas；触控仍然走 `/device/*`。

| 踩过的问题 | 做法 |
|---|---|
| 设备只允许同时跑一路 `screenrecord` | 服务端只做单路编码，再通过队列广播；空闲 8 s 后结束进程 |
| 中途接入时没有关键帧（`A key frame is required`） | 新客户端接入或带 `?fresh=1` 时重新打开编码进程，保证从 SPS+PPS+IDR 开始；前端遇到错误会自动 fresh 重连 |
| Chrome 需要 AVCC 格式，不接受 Annex-B 格式 | 自己拼 avcC（profile/compat/level 加 SPS/PPS），调用 `VideoDecoder.configure({description})`，每帧前加 4 字节长度前缀 |
| 静态画面没有帧（新页面空白） | 先用 `/screen.png` 画出底板，静止超过 2.5 s 时补抓一张保持画面新鲜 |

实测（720×1280 / 6 Mbps）：刷新率从 0.9–9 fps（截图轮询）提升到 **21.5 fps**（有动画时）；从发出输入到画面出现变化，从 340–450 ms 降到 **277–294 ms**；拖拽由跳帧变成连续；码流在有动画时约 2 Mbps，静止时为 0。限制是 `screenrecord` 单次 180 s 到期后会自动重开。

### 2.4 执行层设计（L0 / L1a / L1b / L2）

#### 2.4.1 为什么要分层

现役只有一个执行通道：先截图给模型，模型再返回坐标。实测环境是天翼云手机 `127.0.0.1:10532`，Android 13；该载体已经停用，数据留作对照：

| 项 | 实测 |
|----|------|
| `screencap -p`（720×1600 PNG） | 0.61 / 0.75 / 0.61 s |
| 单步总耗时（截图 + 推理） | 2.5–3.5 s |
| 多步任务 | 让「记录 20 个俯卧撑入印象笔记」跑满 20 步仍然失败（`Reached max step count of 20`） |
| 70 条轨迹工具失败率 | 4 / 191 |

出现这种情况，原因不是模型笨，而是每一步都在重新猜界面，步骤越多，误差和耗时就累加得越厉害。因此执行层拆成四层，按「能不能确定」从上往下使用，把视觉通道负责的步数压到 1–2 步。

#### 2.4.2 L0 确定性命令通道

L0 不把画面交给模型，也不看屏幕，而是直接把交代翻译成 adb 命令，执行完只做一次结果校验。

| 项 | 内容 |
|----|------|
| 能力 | `am start -W` / `am force-stop` / `pm clear` / `pm list packages` / `settings put` / `svc wifi` / `cmd bluetooth_manager` / `input keyevent` / `input swipe` / `screencap` / `logcat -d` / `dumpsys` / `getprop` |
| 实测 | `am start -W -n com.android.settings/.Settings` = **0.12 s**（已缓存）、0.85 s（冷启） |
| 判定成功 | 命令返回码加上 `dumpsys activity activities` 里的 `topResumedActivity` 等于目标 Activity |
| 限制 | ① 任何「需要理解界面」的操作都做不了 ② **中文输入不可用**：`input text "今日做咗20个俯卧撑"` 会直接报 `java.lang.NullPointerException: Attempt to get length of null array`（只能打 ASCII；要输入中文需改用 ADBKeyBoard 广播方式，见附录 C.3） |

#### 2.4.3 L1a 无障碍树通道

L1a 读取系统的无障碍树，拿到带语义的节点（text / resource-id / bounds / role），然后按节点执行动作，不需要猜坐标。

| 项 | 内容 |
|----|------|
| 实现 | 使用常驻的 instrumentation helper（`agent-device` CLI v0.21.31 实测可用，也可以自建） |
| 实测 | 裸跑 `uiautomator dump` 要 **2.25–2.39 s**（每次都要启动 instrumentation）；常驻 helper 快照 **1.12–1.14 s**，内容没有变化时 0.4 s 直接返回「unchanged」 |
| 中文输入 | 需要机内 IME：`agent-device open --test-ime` 加 `fill`（实测中文标题写入成功） |
| 限制一 | **WebView 内容会延迟出现**：无障碍树由 Chromium 侧在 a11y 服务 attach 之后惰性构建。实测印象笔记模板页用 uiautomator 能读到 494 个节点（其中 257 个 TextView 位于 WebView 内）——所以不是读不到，而是**首次访问时经常为空或滞后**，需要重试一次 |
| 限制二 | **富文本编辑器读回不可靠**：`en-note` 的 contenteditable 节点只报告「可编辑、无文本值」，填充之后读回验证会失败（实测 `Android fill verification failed`） |
| 限制三 | 失败的动作会让整帧 `@ref` 失效（实测 `Ref @e4 belongs to an expired ref frame`），必须重新快照，因此每次失败都要多花 1.1 s |

#### 2.4.4 L1b WebView CDP 通道（有条件）

Android WebView 支持 Chrome DevTools 协议，但是**只有宿主 App 调用过 `WebView.setWebContentsDebuggingEnabled(true)`，才会打开对应的 abstract socket**。

| 项 | 内容 |
|----|------|
| 接入 | `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>` → 走 CDP |
| 能力 | `DOM.querySelector` / `Runtime.evaluate` / `Input.insertText`（中文直接注入，**绕过 IME**）/ `Page.captureScreenshot` |
| 速度 | 与 PC 同级：PC 实测读取全页 DOM 的 22 个节点耗时 **2.5 ms**；同机用 uiautomator 对比是 2300 ms，两者相差三个数量级 |
| 实测限制 | 第三方 App 默认不打开调试会话：印象笔记运行时 `/proc/net/unix` 里只能看到 `WebViewZygoteInit`，**没有 `*_devtools_remote` socket**，所以外部接不进去 |
| 可用范围 | 我方可控的 WebView（Portal APK、自家壳、自研 App）一定可用；第三方 App 要等它自己开启；机内 agent（R2）可以在运行时打开 |

#### 2.4.5 L2 视觉通道

Mobilerun 的做法是截图加多模态模型找控件，输出 `click{index}` / `type` / `swipe` 等动作。它**只做兜底**：L0 和 L1 都不认识界面时才使用，步数上限是 20。

#### 2.4.6 路由与降级规则

| 交代类型 | 起点 | 升级条件 |
|----------|------|----------|
| 已在 L0 能力表内（开关 App、改设置、装包、按键、截图） | L0 | 命令失败或前台 Activity 不符 → L1a |
| 原生控件界面（设置、系统 App、多数工具类） | L1a | 快照找不到目标节点，或两轮仍未达成 → L1b（若为 WebView）或 L2 |
| WebView 且我方可控 | L1b | CDP 无 socket / 找不到选择器 → L2 |
| WebView 但第三方 App | L1a 读外壳 + IME 输入 | 正文类富文本 → L2 |
| 游戏、自绘、Canvas | L2 | — |

同一个任务里，每层只试一次，最多降级一轮；到 L2 仍然失败，就发出「要人」信号，并附上最后一张截图和已经执行过的动作列表。

#### 2.4.7 预算与失败处理

| 项 | 值 |
|----|----|
| L0 单步超时 | 10 s |
| L1 单次快照超时 | 8 s；同一界面连续两次快照没有变化，视为卡住 |
| L2 步数上限 | 20（沿用现有设置） |
| 整单预算 | L0 与 L1 合计不超过 30 s，超出就降级到 L2 |
| 失败归因 | 每条历史记录写明「失败在哪一层、最后动作、最后截图」，供人工复核 |

#### 2.4.8 与运维 PRD 的关系

`~/目标/积累/ctyun/cloudphone-ops-agent-prd.md` 描述的是**云手机运维与客服**场景（投诉 → 分配云机 → AI 排查 → 报告）。本设计只复用其中 §3 的 ADB 能力矩阵，作为 L0 的能力目录，不沿用它的产品形态。

#### 2.4.9 落地实现（`layers.py`）

`serve.py` 的 `run_agent()` 第一步调用 `layers.route(text)`；只要命中，就不再启动 Mobilerun。每一层自己判断「接不接这句话」，接不了就返回 `None` 交给下一层。

| 层 | 判定依据 | 动作 | 断言 |
|----|----------|------|------|
| L0 | 正则命中 20 类能力（打开 app / 回桌面 / 关 app / 清数据 / 卸载 / 音量 / 亮度 / Wi-Fi / 蓝牙 / 飞行模式 / 截图 / 装包 / 列包 / 属性 / 开网址 / 点坐标 / 滑动 / ASCII 输入 / 查前台 / 按键） | `am start -W -n`、`input keyevent`、`settings put`、`svc wifi`… | `topResumedActivity` 变为目标包、`settings get` 读回的值一致 |
| L1a | 动词（点击/点开/按/选/打开/进入）+ 目标词 | `agent-device snapshot -i` → label/identifier 精确→包含→去空格模糊 → `input tap` 控件中心 | 前台包发生变化 **或** 快照 hash 发生变化 |
| L1b | 前台 App 有 `@webview_devtools_remote_*` socket | `adb forward` → `/json` → WebSocket `Runtime.evaluate` 找文字元素 `.click()` | JS 返回 `ok:true` |
| L2 | 上三层全部未命中（包括 S 层派不下去） | `mobilerun run` | 由 Mobilerun 自行判定 |

**L0 解析纪律（v0.36）**：① 语气词和补语都要能容忍（`NOISE` 包含 吧/啊/嘛；卸载正则包含 `(?:掉|咗|了|甩)?`），否则「卸载掉X吧」抓不出 app 名；② 别名表要足够全（缺词就靠包名 token 去撞，撞不到就是未命中）；③ **卸载是确定性动作** —— 查不到包名就立即报告「包表没有 X；机上第三方有 N 个」并 `final`，不允许落到 L2 白白点几十秒（只有指代词，例如「这个」「呢个」「佢」，才交给 L1/L2）；卸载完成后要清理 `installed()` 缓存。

**实测（redroid 13 / 720×1280）**

| 层 | 用例 | 耗时 |
|----|------|------|
| L0 | 打开设置 / 回桌面 / 查前台 / 调亮度 120 | 316–399 / 30 / 27 / 89 ms |
| L0 | 卸载（真实卸载）/ 报告未安装 | 165 ms / 27 ms |
| L0 | 查询是否安装（新增语序「X 装咗未」） | 39 ms |
| L1a | 快照（冷 / 暖） | 0.41 s / **0.12 s** |
| L1a | 点「网络和互联网」（设置页，英文 label） | **1.39–1.69 s**（含复核快照） |
| L1b | 网页点按钮 / 填输入框 | **41–56 ms** / 32 ms |
| L2 | 一单多步任务 | 16–25 s |

L1a 还有两个现实约束：① a11y 树用的是**设备语言**（本机是 en-US），中文要靠内置的 `I18N` 映射（网络和互联网 → Network & internet），映射不到就是未命中，不做硬猜；② 只命中 `visibleToUser` 且不属于系统栏的节点，滚动区里尚未展开的条目找不到。

#### 2.4.11 壳侧呈现

执行层的四个格子就是流程图里的常驻组件，不另外开标签页。

| 状态 | 呈现 |
|------|------|
| 命中该层 | 绿框，副标题换成实测耗时（`387 ms`） |
| 未命中 | 标题划线 + 灰显 + `未命中` |
| 未参与 | 灰显 + `未用` |

#### 2.4.13 触发条件公示（`GET /layers`）

「为什么走这一层」不靠猜，接口会直接列出条件；`last_attempts` 回报上一单每一层的结果。

| 层 | 触发条件（全部要满足） | 执行 | 断言 |
|----|------------------------|------|------|
| L0 | 正则命中能力表（打开/关/查有无装/下载安装查重/音量/亮度/开关/截图/点坐标/滑动/ASCII/查前台） | `adb shell` 直连 | `topResumedActivity` / `settings get` / `pm list` 读回 |
| L1a | ① 正则「动词 + 1~12 字目标」② 动词 ∈ {点击,点开,点,按下,按,选择,选,打开,进入,查找,找,搜,搜索,查看,睇,看,填,输入,tap,click} | `agent-device snapshot -i` → 命中控件 → `input tap` 中心 | 前台包发生变化 或 快照 hash 发生变化 |
| L1b | ① 同上「动词+目标」② `/proc/net/unix` 有 **前台 App 的** `@webview_devtools_remote_<pid>` | `adb forward` → `/json` → WebSocket `Runtime.evaluate` | JS 返回 `ok:true` |
| L2 | 上面三层全部未命中 | `mobilerun run` | 由 Mobilerun 自行判定 |

有两处容易踩错的地方，已经修正：

1. **L1b 选错 socket**：手机里可能同时存在几个 WebView 调试 socket（应用宝、WebView shell 各有一个）。原本取第一个，会点到错误的 App。现在改为先执行 `pidof <前台包>`，只认结尾 pid 对得上的那一个 socket。
2. **包名别名写错**：印象笔记国行版包名是 `com.yinxiang`（不是 `com.evernote`），应用宝是 `com.tencent.android.qqdownloader`。别名写错会让「有没有装 X」误答成「未安装」，所以找不到别名时改为列出机器上的第三方 App，不要一口咬定没有安装。

另外增加了「去<app>做X」前缀的处理：先打开 App，再把剩下的意图跑第二轮（例如「去应用宝下载快手」等于先打开应用宝，再判断「下载快手」）。

#### 2.4.14 命中强调与用量统计

- **强调**：命中某一层时，用 Web Animations API 把该层内嵌的 2px 实黄边框闪两下（`rgba(251,191,36,.45) → 1 → .45`，1.1 s ×2），闪完停在绿框加毫秒数上。这里有一个坑：`paint()` 会抹掉 className，所以动画挂在元素本身，另外用 `PULSED` 表保证一单里每层只闪一次（`layerReset()` 负责清表）。
- **查询类先答结论（v0.39）**：凡是问「有没有 / 装了没有」这类问题，一律由包表回答，`result.message` **开头就是结论** —— 例如 `有：com.tencent.mobileqq` 或 `冇：com.tencent.mm`，结论之后才附带层与耗时；`answer=true` 会让日志行标签写成「答案」而不是「完成」。实体名要先剥掉尾缀（`_clean_app_name()`：`QQ这个应用` → `QQ`）。句子里带 `去设置` 也照样回答（老板定的原则：查询意图要的是有还是没有）；像「有没有兴趣」这种既不像 App、又无法解析的说法，不算查询。
- **统计**：服务端用 `LAYER_STATS` 记录每单短路到哪一层，对应层加 1，累计结果写入 `~/.qphone/layer-stats.json`（服务重启也不清零）；`/state`、`/history` 和 `result` 都会带上 `layer_stats` 与 `layer_total`。壳在状态条下面绘制「执行层使用率」：一条堆叠条（L0 蓝 / L1a 绿 / L1b 紫 / L2 黄），加上四层各自的「单数 · 百分比」，页面打开就绘制，不必等任务跑完。

#### 2.4.15 人工接管后续跑

**接管的性质是「人工步骤」委托，而不是任务移交**（2026-10-27 定案）：用户只负责完成 agent 在物理条件或权限上做不到的那一步，做完之后 agent 必须继续执行整个任务，不能当成已经完成。

| 类 | 场景 | 行为 |
|----|------|------|
| **A 人肉步骤** | 登录/注册、验证码/CAPTCHA、付款/订阅、扫码 | `classify_failure()` 命中关键词（或轨迹文件末尾出现 `FastAgentEndEvent`）→ 弹出接管卡 → 用户做完一步 → 继续跑 |
| **B 技术失败** | 模型空想 / malformed / 原地打转 / 步数用尽 / 实际已完成但报失败 | **不弹接管卡**，直接结束并报告原因（`needs_human` 带 `hand_scope:"none"`） |

`need_hand` 带 `hand`（请你做 X）和 `after`（之后我来做 Y），壳显示「请你做：…。其余我来做」，另外提供备注输入框和「我已处理好，继续」按钮。续跑走 `POST /turn/resume`，prompt 里写明「用户**只完成了【X】**，任务还没有完成……只有截图确认目标达成才可以 complete」。

| 细节 | 规则 |
|---|---|
| 步数 | 累计不重置（续跑时用 `of - used`），壳靠 `STEP_BASE` 把前面的步数加回来（Mobilerun 自己从 1 重新计数） |
| 上限 | `QPHONE_RESUME`（默认 3）次；次数用尽或步数用尽就按正常失败收工；B 类不计次数 |
| 卡片 | 续跑用 `resume_started`，复用原来的任务卡，不新开卡片 |
| 权限弹窗 | 通知/存储/定位等属于 B4，由 agent 自动应答，不等待用户 |

#### 2.4.17 语义路由层（S 层）

**一句话概括**：先跑规则（命中时不动用模型，也没有额外延迟）；**三层规则全部未命中，才问模型一次**，只取「意图 + 槽位」，再按路由表派发到 L0 / L1a / L1b。L1a 和 L1b 同样接收语义结果，不只是 L0。

```
L0 规则 → L1a 规则 → L1b 规则 ──全 miss──→ S 层（一次 LLM，只出 JSON）
                                            ├ intent ∈ L0 能力 → L0 执行器
                                            ├ tap              → L1b（有 socket）→ L1a
                                            └ input / search   → L1b（IME 未做）
```

**契约**（模型唯一输出）：`{"intent":"…","app":"","target":"","text":"","confidence":0.0}`
意图白名单：`open_app / check_installed / uninstall / force_stop / clear_data / back / home / screenshot / tap / input / search / scroll / unknown`。

| intent 类 | 派去 | 命令由哪个拼装 |
|---|---|---|
| `open_app` `check_installed` `uninstall` `force_stop` `clear_data` `back` `home` `screenshot` | **L0** | 拼装一句规范说法交给 `l0_try()`（`uninstall+淘宝` → `卸载淘宝`），包名解析、断言和 `final` 全部复用 L0，不另外写一套 |
| `tap` | **L1b** 优先（41–56 ms）→ 不成功再转 **L1a** | `agent-device snapshot` → `input tap` |
| `input` `search` | **L1b**（IME 未做，没有 socket 就走 L2） | CDP `Input.insertText` |

**硬约束**：模型不许输出 shell 或 adb 字符串；包名一律由本地 `resolve_package()` 校验；intent 不在白名单里就直接走 L2。

**校验与降级**：JSON 解析失败重试 1 次；`confidence < 0.6`、不在白名单、超时，都落到 L2，不赌。

**模型与兜底（老板 2026-10-27 拍板）**

- 主力是 **`traework/DeepSeek-V4-Pro-Official`**，超时 8 s；超时或调用不通时自动降级到 **`DeepSeek-V4-Flash-Official`**（2.2–2.6 s）补一次；两个都不行才走 L2
- 按句缓存 24 h（`~/.qphone/sem-cache.json`，最多 200 句）；危险 intent 不做二次确认，靠日志追溯
- 别名自愈：语义命中并且执行成功之后，写入 `~/.qphone/alias-learned.json` 并立即加入 `APP_ALIASES`，下次同样的说法由规则直接命中（不动用模型）

| 模型 | 6 句解析耗时 | 判定 |
|---|---|---|
| `DeepSeek-V4-Pro-Official`（主力） | 2.1 / 4.4 / 4.4 / 4.7 / 5.5 / **27.0** s | 准确但慢（复杂句的 reasoning 有 400–800 token）；`reasoning_effort=minimal` 时 12.3 s、`enable_thinking:false` 时 10.3 s，依然慢 → 必须有 Flash 兜底 |
| `DeepSeek-V4-Flash-Official`（兜底） | 2.2 / 2.5 / 2.6 s | 稳定，3/3 正确 |
| `mimo-v2.6-flash` | 1.6 / 2.1 / 3.6 s | 备选 |
| `glm-5.3-flash` / `qoder/qwen3.8-flash` | 3.9–6.1 s / 超时 ×3 | 不使用 |

|---|---|
| `将淘宝卸咗佢`（三层全部未命中） | 三层 skip → Pro 3.9 s → `uninstall 淘宝` → **L0 55 ms**「未安装」；步骤日志标签 `语义→L0` |
| 同一句话再说一次 | **65 ms**（缓存命中，不动用模型） |
| `帮我睇下百度网盘装咗未` | **39 ms**，走 L0 查询，返回「有装：com.baidu.netdisk」 |
| `揿一下『网络和互联网』` | `tap` → L1b 没有文字 → L1a 报「无障碍树冇呢个控件」，如实未命中 |

**开关与自查**：`QPHONE_SEM=0` 可以整体关闭；`QPHONE_SEM_MODEL`、`QPHONE_SEM_FALLBACK`、`QPHONE_SEM_TIMEOUT` 可以调整；`GET /layers` 会返回 `semantic` 字段（包含模型、超时、缓存、统计和上一次解析结果）。

**本版不做**：多步任务拆解（仍然落到 `unknown` 再进 L2）、`scroll` 执行器、中文 IME 输入。

#### 2.4.18 装应用快路径（v0.39）

原本「下载安装 X 并打开」实测需要 **18 步**，针对四个成因逐个处理：

| 成因 | 浪费 | 做法 | 作用在哪一层 |
|---|---|---|---|
| 没有商店概念：靠视觉翻抽屉找商店 | 5 步 | `stores()` 用 `pm list packages` 对照 14 条商店表（应用宝→小米→华为→…→Google Play 排最后）；L0 直接打开排在第一个的商店 | **事实层**（先用 adb 查清） |
| 开屏广告 + 点搜索框被弹去广告 | 3 步 | `STORE_SEARCH_ACT` 直接落到 `com.tencent.nucleus.search.SearchActivity`，跳过 Splash 页 | **路由层**（多一条确定性入口） |
| 中文输入不了（`input text` 打中文会 NPE） | 卡死 | `input_text()` 安装 ADBKeyBoard，用 broadcast 发送 unicode；没有安装就退回 `input text`（只支持 ASCII） | **执行层**（L0 的输入文字能力） |
| 装完之后对着「Installing…」空等 | 5–6 步 | `_install_watcher()` 每 2 s 查一次包表：装好就 `am start`（被弹窗挡住就退一步重试 3 次）、`pm grant` 通知权限、`terminate` 模型 | **收尾判定层**（用 adb 确认，取代模型自述） |

另外：`l2_next` 让打开商店之后直接落到 L2（不再扫 L1a 和 L1b，省下约 7 s）；指代词（「佢」「呢个」）不作为控件名使用；`install_target()` 统一抽取应用名（修正「安装快手」被误抓成 app 名的问题）；补充百度贴吧、快手极速版的别名。

**实测**：百度贴吧 18 步 → 高德地图 **5 步**（装完立刻收尾，`com.autonavi.minimap`）；腾讯地图 13 步（模型自己完成，前台 `com.tencent.map` 已核实）。

## 3. 用户界面详细设计

### 3.1 界面结构

主界面就是壳里的对话窗口，本文不重新绘制这个界面。

云机的画面不是主界面，也不放进壳里。需要人接手的时候，画面会在云机那一侧打开。

### 3.2 处理流程与约束

人在对话里输入一句话。如果系统提示需要人接手，人就去云机那一侧看这台机器，不要求把画面传回当前电脑。

约束：壳不写死平台，也不写死云机的来源。更换云机（容器换成租用实例）时只改控制程序，壳一行代码都不用动。

模型地址由人在控制程序一侧填写，本文不代为填写。

**结果卡的配色约束**：结果行 `.t-dt` 使用 `var(--fg)`（亮色主题下实测对比度为 16.5:1），步数行 `.t-step` 使用 `var(--soft)`（对比度 6.3:1）；暗色主题通过 `html[data-theme="dark"]` 单独保留原来的浅色值。不要再写死 `#cfd8e3`、`#e9d9a8` 这类只适合暗色的颜色，否则在亮色主题下会出现「看不见字」的问题。

## 附录 C 执行层 L0 能力清单

L0 是**确定性命令层**：靠正则表达式和包名表直接下手，**不调用任何模型**。目前覆盖 20 项能力、68 条别名，分成五大类。

进入 L0 之前有两道预处理：第一步清掉语气词和客套词（例如「帮我」「唔该」「一下」「吧」「啊」「嘛」「咯」）；第二步查 68 条别名表（例如 应用宝、百度网盘、360浏览器、抖音、小红书、百度贴吧），语义层学到的新别名会写入 `~/.qphone/alias-learned.json`。
