## 2. 综合描述

### 2.1 系统目标

人在对话里交代一件事。事由控制程序在云 Android 上做完。卡住或做完，才回到对话。屏幕不是主界面。

### 2.2 系统概述

三块，调用方向固定。

| 程序 | 位置 | 现在 |
|------|------|------|
| 客户端 | 薄壳，形态未定（2026-10-22 删 Rakazo） | 未建。只发交代、只收进度与结果，不含 agent、不带电脑容器。 |
| 控制程序 | 近云机一侧（正式在 Ubuntu 虚拟机；临时在 Mac） | 未接。框架定 Mobilerun。 |
| 云机 | redroid 容器（正式）／天翼云手机（临时） | 临时载体已实测可操作。 |

客户端只管收和发。操作发生在控制程序一侧：它调本机（或转发口）adb。人要看屏幕时在云机一侧看，不把画面转到客户端。

### 2.3 运行环境

| 项 | 正式 | 临时（2026-10-22 起） |
|----|------|------------------------|
| 环境 | 现有远程 Windows 上的 Ubuntu 虚拟机 | 天翼云手机（远端） |
| 内存 | 虚拟机 8G，只稳开一部云机 | 不适用 |
| 云机镜像 | `redroid/redroid:13.0.0_64only-latest` | 中国电信 `Tianyi1Hao2021` / `AURORA` |
| 云机系统 | Android 13 x86_64 | Android 13，SDK 33，**arm64-v8a** |
| 云机入口 | 虚拟机内 `127.0.0.1:5555` | Mac 本机 `127.0.0.1:<客户端转发端口>`，**每次会话都变**（实测 10532） |
| 客户端 | 薄壳，形态未定 | 同左。候选：Telegram / Hermes 桌面顶，或自写 Tauri/Electron 薄壳 |
| 对照 | 同一台虚拟机里的 A9。留着。不作为本设计的运行程序 | 同左 |

**天翼云手机实测（2026-10-22）**：`adb connect 127.0.0.1:10532` 通；`getprop` 得 SDK 33、`arm64-v8a`、`ChinaTelecom`；`/system/bin/uiautomator` 在；`enabled_accessibility_services` 为 `null`（未开）。`adb install` + `am start` + `screencap` 三条都真跑过：装 `com.example.splashscreen` 并打开，截图见画面真起。

**2026-10-19 已核实（正式底座）**：在虚拟机内对 `127.0.0.1:5555` 点相册图标，相册打开。从 Mac 经转发发回主屏，也能回到桌面。同一条转发上，看屏连接失败过、大截图传断过，所以联调不走 Mac 转发。

**Mobilerun 实测（2026-10-22）**：`mobilerun` v0.7.0 装喺控制机（今日 Mac），Portal APK 0.7.27（51.1 MB）装落云机；`mobilerun ping` 回「Portal is installed and accessible」，无障碍服务自动开启；`mobilerun device ui` 取到无障碍树（720×1600）。`mobilerun run "打开设置，睇下 Android 版本"` 6 步自动完成，答 Android 13 / CloudPhone / ud710，截图核对一致 —— **验收③「自动操作一步」已通**。模型走后端 Qbridge `127.0.0.1:7863/v1`。

**未核实**：redroid 是 x86_64，Mobilerun Portal APK 有无 x86_64 变体未知；没有就退 `portal_mode: disabled` 走 UIAutomator（中文输入会坏）。

### 2.4 程序结构说明

| 最终程序 | 种类 | 谁调用它 |

这台虚拟机可以编译。A9 就是在这里编译出来的，编译产物不删。那是对照，不是这一部的组装方式。

## 3. 系统详细设计

### 3.1 云机

#### 3.1.1 程序特征

正式：现成容器，镜像 `redroid/redroid:13.0.0_64only-latest`，不是本项目编译出来的可执行文件。
临时：天翼云手机，租用实例，同样不是本项目编译。

#### 3.1.2 功能

提供一部可操作的 Android。装应用、打开应用、接受点击、给出画面，都通过 adb。不在云机里放控制逻辑。

#### 3.1.3 输入 / 输出

| 方向 | 项 | 说明 |
|------|----|------|
| 输入 | adb 连接 | 正式 `127.0.0.1:5555`；临时 Mac 转发口 |
| 输入 | `adb install` | 安装指定安装包 |
| 输入 | `adb shell input` | 点击、按键 |
| 输入 | `adb shell am` | 打开应用 |
| 输出 | 命令返回 | 成功或失败原因 |
| 输出 | `screencap` | 当前画面。给人接手时用，不作为主界面 |

不向客户端提供屏幕和控制入口。

#### 3.1.4 数据结构

正式：容器内的应用数据在容器数据盘。关机不删这盘。清空要另下指令。盘的路径未定，见附录 B5。
临时：数据在天翼侧，本项目不可控、不可清空。

#### 3.1.5 调用关系

被控制程序调用。不被客户端调用。

#### 3.1.6 算法

无自有算法。

#### 3.1.7 限制

一部。8G 虚拟机上不并行开第二部。天翼云手机同时只连一部，转发端口每会话都变。x86 上的 ARM 应用，没在正式底座上打开过，不算能用。

### 3.2 控制程序

#### 3.2.1 程序特征

框架定 **Mobilerun**（MIT，开源 Python 包，不是它的托管云）。它本身就是手机原生 agent：带 `click / long_press / type / swipe / open_app / get_state / take_screenshot / complete` 等手机工具，看屏走无障碍树 + 截图两路。

配套层 `qphone.py`（本仓库）只做 Mobilerun 不管的事：容器起停、开机状态、端口发现、装包、截图。它不做决策，也不调模型。

#### 3.2.2 功能

接收一句交代。在云机上做完，或说出失败原因。做的过程中回报进度。需要人看屏幕时，发出要人，并停在云机一侧。做完发出结果。开机、关机的状态要说得清。

人不用填端口。正式就是本机 `127.0.0.1:5555`；临时由 `qphone.py` 自动发现转发口。

#### 3.2.3 输入 / 输出

| 方向 | 项 | 说明 |
|------|----|------|
| 输入 | 交代 | 来自客户端的一句话，或一个安装包 / 应用名 |
| 输出 | 进度 | 正在做哪一步 |
| 输出 | 要人 | 卡住。人到云机侧看屏幕，不转到客户端 |
| 输出 | 结果 | 做成，或失败原因 |
| 输出 | 状态 | 开、关、能不能操作 |
| 对云机 | adb | 正式 `127.0.0.1:5555`；临时 Mac 转发口 |

对话来回只有这五种。字段名未定，见附录 B1。

#### 3.2.4 数据结构

未建。不编一套假的表。

#### 3.2.5 调用关系

客户端把交代送到控制程序的接口。控制程序只调云机 adb，不把 scrcpy 或屏幕流转到客户端。

**通道（2026-10-22 定并已实现）**：

```
POST /turn   {text: "交代"}
  ← 事件流：progress / needs_human / result / status
```

壳只认这四种事件，不认云机地址、不认 adb。控制程序跑在哪台机、云机是容器还是租用实例，壳都不需要知道。接口层包住 Mobilerun 的调用与结果。

实现：`serve.py`（同仓库，零依赖，默认 `127.0.0.1:8777`）。壳页 `GET /`（`shell.html`）；步骤回放 `GET /replay?id=<轨迹>`（Mobilerun `--save-trajectory step` 出嘅每步截图 + 思考 + 动作）；截图 `GET /traj/<id>/screenshots/<f>`。`GET /health`、`GET /status`、`POST /turn`（SSE）。**已实测两条路径**：① 成功 —— `"打开设置，睇下 Android 版本"` 回 `status → progress×N → result{success:true}`，答案 Android 13；② 失败 —— `"打开图库，睇下有几多张相"` 图库本身无相，agent 8 步用尽，回 `needs_human{reason:"Reached max step count of 8 steps"} → result{success:false}`。云机未连时回 `status{state:"not_ready"} → needs_human → result{success:false}`，唔会挂住。

#### 3.2.6 算法

第一版只要求做透一个场景（见附录 B3）。Mobilerun 直跑用 `mobilerun run "..."`；要看图加 `--vision`，要多步规划加 `--reasoning`。

⚠️ 已踩：`--provider OpenAI` 会按官方模型白名单校验，自定义模型名（Qbridge 的 `workbuddy/deepseek-v4.1-flash`）直接被拒（`Unknown model`）。要走本地 OpenAI 兼容端点，用 `--provider DeepSeek --api_base http://127.0.0.1:7863/v1`。

#### 3.2.7 处理顺序

1. 收到交代。
2. 确认云机可操作。不可操作则返回状态和失败原因，停止。
3. 若交代是安装或打开，先经 adb 做完，返回结果。
4. 若要操作界面，交 Mobilerun 执行，逐步回报进度。
5. 做不下去，发要人，人在云机侧接手。
6. 收到关机交代，关掉这部，返回状态。

### 3.3 客户端

#### 3.3.1 程序特征

薄壳，未建。只做三件事：收一句交代、显示进度、显示结果（含要人）。不含 agent、不带电脑容器、不依赖 docker。

2026-10-22 原拟用现成 Rakazo 桌面，**已完整删除**（容器、镜像、数据卷、源码目录一并清掉）。理由：Rakazo 自带 agent 与「电脑」容器，与「客户端只系壳」冲突；两层 agent 串埋会 token 双花、步数放大、出错分不清哪层。同日亦否决 dsh 桌面（同属自带 agent 的 harness，不是壳）。

候选形态（择一，未定，见附录 B7）：① 先用 Telegram / Hermes 桌面顶，零开发；② 自写薄壳（Tauri 或 Electron），可打包三端。

#### 3.3.2 功能

给人一个对话入口。发出交代。显示进度、要人、结果、状态。不在客户端打开云机画面，不在客户端点云机。

#### 3.3.3 输入 / 输出

| 方向 | 项 |
|------|----|
| 输入 | 人输入的交代 |
| 输出 | 发给控制程序的交代 |
| 输入 | 控制程序返回的进度、要人、结果、状态 |
| 输出 | 显示给人 |

壳只调 `POST /turn` 与事件流。壳不连 adb，不认云机是怎么来的。

#### 3.3.4 数据结构

未定。壳只保留对话显示，不存云机状态，不存 adb 地址。

#### 3.3.5 调用关系

人调用壳。壳只调用控制程序接口。壳不调用云机 adb，也不调用 `127.0.0.1:5555`（那个地址不在壳这一侧）。

#### 3.3.6 算法

无。

## 4. 用户界面详细设计

### 4.1 界面结构

主界面是壳里的对话。本文不重画这个界面。

云机画面不是主界面，也不出现在壳里。要人接手时，画面在云机一侧打开。

### 4.2 处理流程与约束

人在对话里输入。看到要人之后，到云机一侧看那部机器，不要求把画面转到当前电脑。

约束：壳不写死平台，也不写死云机来源。换云机（容器 ↔ 租用实例）只改控制程序，壳一行不动。

模型地址由人在控制程序一侧填写。本文不代填。
