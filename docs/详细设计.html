2. 综合描述

2.1 系统目标

一句话：一部 24×7 嘅云 Android 手机 + 三条任务。人讲一句，云机做完，回一句有证据嘅结果。屏幕不是主界面。

要跑通嘅就三条（详 docs/落地目标清单.md，2026-10-27 定稿，唔再加）

编号 场景 判定（adb 机核，唔靠模型自述）
G1 开音乐 App → 目标歌单 → 指定歌 → 点播 dumpsys media_session：state = PLAYING，且 title 命中歌名
G2 只有移动端嘅 App → 发带图动态（Soul 只系例子） 回「我的 → 动态」列表，snapshot 命中本次文字 + 带图
G3 教育类 App → 做题 / 考试 结果页见到得分 / 已交卷，或列表状态 未做 → 已完成

三条共同底线
1. 判定一律 adb 机核（media_session / snapshot 文本 / 列表状态），唔信模型讲「做完」
2. 有确定性路径就唔落 L2；落 L2 要有步数上限
3. 登录、验证码、滑块、人脸 —— 一律弹接管，程序唔硬闯

唔喺目标内（防止范围再膨胀）：有网页 / 有 API 嘅平台（走 API，唔用云机）· 听写口语拍照上传（云机冇麦克风、冇摄像头）· 主观题代写 · 「咩都做到」嘅通用 agent。

共同卡口：三个场景都要登录（手机号 + 验证码），且都系新设备异地登录。所以第一步系「登录态准备」，唔系写码。

三块，调用方向固定。

3. 系统详细设计

架构总览 · 执行分层

一句交代按「能唔能确定」由上往下用：L0 确定性命令 → L1a 无障碍树 → L1b WebView CDP → L2 视觉兜底。
视觉只做兜底，负责步数压到 1–2 步；判定细则、实测与落地见 §3.4。

原架构图 v0.8 已于 2026-10-26 并入本文，架构图只此一份（旧 架构图.html 已删除）。

三类边界 内容
用户看见的 对话，不是远程桌面；卡住才把屏幕递过来；一句话关机，状态说得清
第一版要跑通的 一部云手机，不用手填端口；借现成项目完成装包和点一步；另一台干净机器按文档能复现
不在这张图里承诺的 集群、移动端、Windows；容器二选一已经定死；系统服务这周就编进镜像

每层自己只手（四只手各管各，互不依赖）

层 自己只手 通道
L0 adbd（系统命令，唔使装任何嘢） am start / am force-stop / pm uninstall / pm clear / pm list packages / settings put / input
L1a snapshothelper（机内无障碍 helper com.callstack.agentdevice.snapshothelper v0.21.31） adbd 叫佢出无障碍树 + 派发点击

3.1 云机

3.1.1 程序特征

现成容器，镜像 redroid/redroid:13.0.0_64only-latest（arm64），不是本项目编译出来的可执行文件。
唯一执行目标：localhost:5556 → 容器内 5555，由 scripts/redroid-up.sh 起停。
已排除（2026-10-26）：本机 AVD 模拟器（已删）、天翼云手机（不再使用）。

3.1.2 功能

提供一部可操作的 Android。装应用、打开应用、接受点击、给出画面，都通过 adb。不在云机里放控制逻辑。

3.1.3 输入 / 输出

方向 项 说明
输入 adb 连接 localhost:5556 → 容器 5555（QPHONE_TARGET 默认值；容器起停见 scripts/redroid-up.sh）
输入 adb install 安装指定安装包
输入 adb shell input 点击、按键
输入 adb shell am 打开应用
输出 命令返回 成功或失败原因
输出 screencap 当前画面。给人接手时用，不作为主界面

不向客户端提供屏幕和控制入口。

3.1.4 数据结构

数据在 Docker 命名卷 qphone-data（住在 VM 的 ext4 上），抹掉容器数据仍在；要清空 docker volume rm qphone-data。

为什么不用宿主目录：-v ~/redroid13-data:/data 会经 colima 的 virtiofs，/data 变成 type virtiofs；Android vold 要 ext4 project quota（FS_IOC_FSGETXATTR），virtiofs 回 Inappropriate ioctl for device，于是 StorageManager / MediaProvider 一路报存储有问题。实测换成命名卷后 /data 是 type ext4、错误条数 0。

⚠ 变量名撞车：REDROID_DATA（宿主目录，调试用）与 REDROID_DATA_VOLUME（默认 qphone-data）。默认走卷，只有显式给 REDROID_DATA 才用宿主目录。

3.1.5 调用关系

被控制程序调用。不被客户端调用。

3.1.6 算法

无自有算法。

3.1.7 限制

一部。VM 内不并行开第二部。端口用 5556（5555 曾被本机 AVD 占用，虽然 AVD 已删，但端口沿用，避免与「5555 其实是模拟器」的旧认知混淆）。redroid 无 GMS，依赖 Play 服务的 App 装得上但跑唔起，要另配 OpenGApps。adb shell input text 打中文仍 NPE。

3.1.8 载体实测对照（历史记录；AVD / 天翼云已排除）

项 天翼云手机 本地 AVD 本地 redroid 13
screencap -p 0.61–0.75 s 0.42–0.66 s 0.34 s
uiautomator dump 2.25–2.39 s 2.0–2.2 s 1.95 s
L1a 快照（冷/暖） 1.12 s 0.51–0.58 s 1.12 / 0.42 s
L0 am start -W 0.12 s（暖） 0.43 / 0.14 s 0.41 / 0.04 s
L2 一单「打开设置」 20 步未完 3 步 / 30 s 2 步 / 16.3 s

结论：redroid 最快；uiautomator dump 约 2 s、L2 单步 7–8 s 系 Android 与模型侧成本，换设备唔变 —— 所以 L0 优先、L1 常驻、L2 只兜底。

redroid 四个坑（实测）：① 必须 _64only 镜像（普通版 32 位 vendor 二进制 → Exec format error → 容器 Exited 129）；② modprobe binder_linux 只令 /proc/filesystems 出现 binder，要 mount -t binder binder /dev/binderfs 才产节点；③ 节点默认 600，容器内要 chmod 666；④ 绑节点用 -v，--device 会 ENXIO。前置：VM 要装 linux-modules-extra，启动参数加 androidboot.use_memfd=true（5.18+ 无 ashmem）。整套已封成 scripts/redroid-up.sh。

3.1.9 存储（/data）

项 值
后端 Docker 命名卷 qphone-data（VM 内 /dev/root ext4）
设备内看到 /data = ext4、18 GB（跟着 VM 盘走），/storage/emulated = /dev/fuse
持久性 删容器不丢；docker volume rm qphone-data 才清
扩容 扩 colima VM 盘（colima stop && colima start --disk <GB>），设备侧无需改
反例 挂宿主目录 → virtiofs → vold 拿唔到 project id → 系统提示存储有问题（已实测）

3.2 控制程序

3.2.1 程序特征

框架定 Mobilerun（MIT，开源 Python 包，不是它的托管云）。它本身就是手机原生 agent：带 click / long_press / type / swipe / open_app / get_state / take_screenshot / complete 等手机工具，看屏走无障碍树 + 截图两路。

配套层 qphone.py（本仓库）只做 Mobilerun 不管的事：容器起停、开机状态、端口发现、装包、截图。它不做决策，也不调模型。

3.2.2 功能

接收一句交代。在云机上做完，或说出失败原因。做的过程中回报进度。需要人看屏幕时，发出要人，并停在云机一侧。做完发出结果。开机、关机的状态要说得清。

人不用填端口。正式就是本机 127.0.0.1:5555；临时由 qphone.py 自动发现转发口。

3.2.3 输入 / 输出

方向 项 说明
输入 交代 来自客户端的一句话，或一个安装包 / 应用名
输出 进度 正在做哪一步
输出 要人 卡住。人到云机侧看屏幕，不转到客户端
输出 结果 做成，或失败原因
输出 状态 开、关、能不能操作
对云机 adb 正式 127.0.0.1:5555；临时 Mac 转发口

对话来回只有这五种。字段名未定，见附录 B1。

3.2.4 数据结构

未建。不编一套假的表。

3.2.5 调用关系

客户端把交代送到控制程序的接口。控制程序只调云机 adb，不把 scrcpy 或屏幕流转到客户端。

通道（2026-10-22 定并已实现）：

POST /turn   {text: "交代"}
  ← 事件流：progress / needs_human / result / status

壳只认这四种事件，不认云机地址、不认 adb。控制程序跑在哪台机、云机是容器还是租用实例，壳都不需要知道。接口层包住 Mobilerun 的调用与结果。

实现：serve.py（同仓库，零依赖，默认 127.0.0.1:8777）。壳页 GET /（shell.html）；步骤回放 GET /replay?id=<轨迹>（Mobilerun --save-trajectory step 出嘅每步截图 + 思考 + 动作）；截图 GET /traj/<id>/screenshots/<f>。GET /health、GET /status、POST /turn（SSE）。已实测两条路径：① 成功 —— "打开设置，睇下 Android 版本" 回 status → progress×N → result{success:true}，答案 Android 13；② 失败 —— "打开图库，睇下有几多张相" 图库本身无相，agent 8 步用尽，回 needs_human{reason:"Reached max step count of 8 steps"} → result{success:false}。云机未连时回 status{state:"not_ready"} → needs_human → result{success:false}，唔会挂住。

3.2.6 算法

第一版只要求做透一个场景（见附录 B3）。Mobilerun 直跑用 mobilerun run "..."；要看图加 --vision，要多步规划加 --reasoning。

⚠️ 已踩：--provider OpenAI 会按官方模型白名单校验，自定义模型名（Qbridge 的 workbuddy/deepseek-v4.1-flash）直接被拒（Unknown model）。要走本地 OpenAI 兼容端点，用 --provider DeepSeek --api_base http://127.0.0.1:7863/v1。

3.2.7 处理顺序

  1. 收到交代。
  2. 确认云机可操作。不可操作则返回状态和失败原因，停止。
  3. 若交代是安装或打开，先经 adb 做完，返回结果。
  4. 若要操作界面，交 Mobilerun 执行，逐步回报进度。
  5. 做不下去，发要人，人在云机侧接手。
  6. 收到关机交代，关掉这部，返回状态。

3.3 客户端

3.3.1 程序特征

薄壳，未建。只做三件事：收一句交代、显示进度、显示结果（含要人）。不含 agent、不带电脑容器、不依赖 docker。

2026-10-22 原拟用现成 Rakazo 桌面，已完整删除（容器、镜像、数据卷、源码目录一并清掉）。理由：Rakazo 自带 agent 与「电脑」容器，与「客户端只系壳」冲突；两层 agent 串埋会 token 双花、步数放大、出错分不清哪层。同日亦否决 dsh 桌面（同属自带 agent 的 harness，不是壳）。

候选形态（择一，未定，见附录 B7）：① 先用 Telegram / Hermes 桌面顶，零开发；② 自写薄壳（Tauri 或 Electron），可打包三端。

3.3.2 功能

给人一个对话入口。发出交代。显示进度、要人、结果、状态。不在客户端打开云机画面，不在客户端点云机。

3.3.3 输入 / 输出

方向 项
输入 人输入的交代
输出 发给控制程序的交代
输入 控制程序返回的进度、要人、结果、状态
输出 显示给人

壳只调 POST /turn 与事件流。壳不连 adb，不认云机是怎么来的。

3.3.4 数据结构

未定。壳只保留对话显示，不存云机状态，不存 adb 地址。

3.3.5 调用关系

人调用壳。壳只调用控制程序接口。壳不调用云机 adb，也不调用 127.0.0.1:5555（那个地址不在壳这一侧）。

3.3.6 算法

无。

3.3.7 实况窗触控

点击 = 点云机，拖动 = 滑动，另有三键。接口（POST JSON，做完即刻抓一帧令壳见到反应）：/device/tap {x,y}、/device/swipe {x1,y1,x2,y2,ms}、/device/key {key}（back/home/appswitch/menu/enter/del/power/wakeup/sleep）、/device/home。

坐标换算（画面 object-fit:contain，唔可以直接用元素宽高）：

k  = min(boxW/720, boxH/1280)
ox = imgLeft + (boxW - 720k)/2 ,  oy = imgTop + (boxH - 1280k)/2
x_dev = (clientX - ox)/k ,        y_dev = (clientY - oy)/k

判定：位移 <9 px 且 <600 ms → tap；否则 swipe（ms 取按住时长，夹 80–900）。离线时唔送输入。实测：input tap 本身 30–44 ms、swipe 0.27–0.31 s、接口往返（含抓帧）tap 134–402 ms、swipe 441–452 ms。

3.3.8 实况直播（H.264）

链路：screenrecord --output-format=h264 - → adb exec-out → serve 切 NAL 广播（[4B len][1B kind][4B ts][payload]）→ 浏览器 VideoDecoder 硬解 → canvas；触控仍走 /device/*。

踩过嘅问题 做法
设备只允许一路 screenrecord 服务端单路编码 + 队列广播；空闲 8 s 收进程
中途接入冇关键帧（A key frame is required） 新客户端 / ?fresh=1 时重开编码进程，保证由 SPS+PPS+IDR 开始；前端遇错自动 fresh 重连
Chrome 要 AVCC 唔要 Annex-B 自拼 avcC（profile/compat/level + SPS/PPS），VideoDecoder.configure({description})，每帧 4 字节长度前缀
静态画面冇帧（新页空白） 用 /screen.png 画底板，静止 >2.5 s 补一张保鲜

实测（720×1280 / 6 Mbps）：刷新率 0.9–9 fps（截图轮询）→ 21.5 fps（动画面）；发输入到画面见变化 340–450 ms → 277–294 ms；拖拽由跳帧变连续；码流约 2 Mbps（动画面）、静止 0。限制：screenrecord 单次 180 s 到期自动重开。

3.4 执行层设计（L0 / L1a / L1b / L2）

3.4.1 为什么要分层

现役只有一个执行通道：截图给模型、模型给坐标。实测（天翼云手机 127.0.0.1:10532，Android 13；该载体已停用，数据留作对照）：

项 实测
screencap -p（720×1600 PNG） 0.61 / 0.75 / 0.61 s
单步总耗时（截图 + 推理） 2.5–3.5 s
多步任务 「记录 20 个俯卧撑入印象笔记」跑满 20 步仍失败（Reached max step count of 20）
70 条轨迹工具失败率 4 / 191

原因不是模型笨，是每一步都在重新猜界面，步骤越多误差与耗时累加。故拆成四层，按「能不能确定」从上往下用，把视觉通道的负责步数压到 1–2 步。

3.4.15 人工接管后续跑

接管 = 「人肉步骤」委托，唔系任务移交（2026-10-27 定案）：用户只做 agent 物理/权限上做唔到嗰一步，做完 agent 必须继续成个任务，唔可以当完咗。

细节 规则

3.4.17 语义路由层（S 层）

一句话：规则先跑（命中就 0 模型、0 延迟）；三层规则全 miss 才问一次模型，只拿「意图 + 槽位」，再按路由表派去 L0 / L1a / L1b。L1a、L1b 一样食语义，唔止 L0。

L0 规则 → L1a 规则 → L1b 规则 ──全 miss──→ S 层（一次 LLM，只出 JSON）
                                            ├ intent ∈ L0 能力 → L0 执行器
                                            ├ tap              → L1b（有 socket）→ L1a
                                            └ input / search   → L1b（IME 未做）

契约（模型唯一输出）：{"intent":"…","app":"","target":"","text":"","confidence":0.0}
意图白名单：open_app / check_installed / uninstall / force_stop / clear_data / back / home / screenshot / tap / input / search / scroll / unknown。

intent 类 派去 命令由边个拼
open_app check_installed uninstall force_stop clear_data back home screenshot L0 组一句规范讲法交 l0_try()（uninstall+淘宝 → 卸载淘宝），包名解析 / 断言 / final 全部复用 L0，唔另写一套
tap L1b 优先（41–56 ms）→ 唔得转 L1a agent-device snapshot → input tap
input search L1b（IME 未做，冇 socket 即 L2） CDP Input.insertText

硬约束：模型唔准出 shell／adb 字符串；包名一律本地 resolve_package() 校验；intent 唔在白名单 → 直接 L2。

校验与降级：坏 JSON 重试 1 次；confidence < 0.6、白名单外、超时 → 落 L2，唔赌。

模型与兜底（老板 2026-10-27 拍板）

4. 用户界面详细设计

4.1 界面结构

主界面是壳里的对话。本文不重画这个界面。

云机画面不是主界面，也不出现在壳里。要人接手时，画面在云机一侧打开。

4.2 处理流程与约束

人在对话里输入。看到要人之后，到云机一侧看那部机器，不要求把画面转到当前电脑。

约束：壳不写死平台，也不写死云机来源。换云机（容器 ↔ 租用实例）只改控制程序，壳一行不动。

模型地址由人在控制程序一侧填写。本文不代填。
结果卡（.task）配色约束：结果行 .t-dt 用 var(--fg)（亮色实测对比 16.5:1），步数行 .t-step 用 var(--soft)（6.3:1）；暗色用 html[data-theme="dark"] 单独保留原浅色值。⚠️ 唔可以再写死 #cfd8e3 / #e9d9a8 一类暗色专用色——亮色主题下会变「睇唔到字」。
