# QPhone 三级执行方案 v0.1（L0 确定性 / L1 结构 / L2 视觉）

> 2026-10-23 · 起因：纯 GUI（截图 + 视觉模型）方案时效与失败率过高
> 实测设备：天翼云手机 `127.0.0.1:10532`（Android 13 / SDK 33 / arm64）
> 本文件只写跑过嘅数，冇跑过嘅标注「待验」

---

## 1. 问题：纯 GUI 到底慢/错在哪

| 事实 | 实测 | 来源 |
|:--|:--|:--|
| 每步感知：`screencap -p`（720×1600 PNG） | **0.61 / 0.75 / 0.61 s** | 3 次 `time` |
| 每步感知 + 推理 | 2.5–3.5 s | 由 trajectory 步数与日志推算 |
| 20 步任务全程 | ≥ 60 s，仍可能失败 | 见下 |
| 「打开设置」类单步任务 | 1–3 步，成功 | 70 条 trajectory 中该类基本全成 |
| 「记录 20 个俯卧撑入印象笔记」 | **跑满 20 步 → `Reached max step count of 20`** | `trajectories/20261023_170154_64d93030` |
| 另一单 | `Model produced malformed tool-call markup 3 consecutive times` | `trajectories/20261023_162259_ae97dcc6` |
| 工具执行失败率 | 4 / 191（2%），但失败集中在多步任务 | 70 条 trajectory 汇总 |

结论：**单步便宜、累计贵、错一次就整单报废**。视觉模型每一步都要重新「看懂」界面，步骤一多，误差与耗时指数累积。

## 2. 三条通道实测对比（同一云机）

| 通道 | 命令 | 单次耗时 | 信息量 | 备注 |
|:--|:--|:--|:--|:--|
| **L0 确定性** | `am start -W -n com.android.settings/.Settings` | **0.12 s（已缓存）/ 0.85 s（冷启）** | 无（直接到达目标态） | 0 模型、0 截图、0 不确定性 |
| **L1 结构** | `uiautomator dump` 裸跑 | **2.25 / 2.29 / 2.33 / 2.39 s** | 36 节点（22 个带 text） | 每次都要起 instrumentation，**太慢** |
| **L1 结构（常驻）** | `agent-device snapshot`（persistent helper） | **1.12 / 1.14 / 1.13 s**；内容无变时 0.4 s 返回「unchanged」 | 24–39 个可见节点 + `@ref` | 比裸 dump 快一倍，且可去重 |
| **L2 视觉** | `screencap` + LLM | 2.5–3.5 s/步 | 全画面像素 | 兜底用 |

**关键结论**：在这台**云**手机上，ADB 转发本身有 ~0.6 s 底噪，所以「结构性感知」不会自动变快；L1 嘅价值在于**准确性**（直接拿到 text / id / bounds，不用猜），L0 嘅价值才是**提速**（0.1 s 级）。

## 3. 实测撞到嘅三个硬障碍（必须写进设计）

1. **中文输入**：`adb shell input text "今日做咗20个俯卧撑"` → `java.lang.NullPointerException: Attempt to get length of null array`。纯 ADB 只能打 ASCII。
   → 必须走**机内 IME 注入**：Portal APK / agent-device `--test-ime`（实测填入中文标题成功，4.4 s 含 settle）。
2. **WebView 内容区不可靠（L1 盲点）**：印象笔记正文 `webview` 内 `text-field "en-note"` 填充后 **`Android fill verification failed`**（读回验证失败）；`type` 报「Typed 18 chars」但实际落到别的页面。
   → L1 对 hybrid app / 编辑器类界面无效，必须降级 L2 视觉。
3. **ref 过期**：一次失败动作会让 `@ref` 整帧失效（`Ref @e4 belongs to an expired ref frame`），需要重新 snapshot —— 每次失败多 1.1 s。

## 4. 三级架构

```
用户一句交代
   │
   ▼
[路由器] 任务 → 能力判定（本地规则 + 可选模型）
   │
   ├── L0 确定性通道 ── 命中就用，0 模型
   │     am start / am force-stop / pm clear / pm list
   │     settings put / input keyevent / input text(ASCII)
   │     content query / sqlite / dumpsys / getprop / cmd wifi|bluetooth
   │     → 0.1–0.9 s，成功确定
   │
   ├── L1 结构通道 ── 快照 + selector/ref 动作
   │     persistent helper（agent-device 或自建 instrumentation）
   │     press / fill / scroll / back by `text=` `id=` `role=`
   │     → 1.1 s/步，步骤数比视觉少（直接命中语义节点）
   │
   └── L2 视觉通道 ── 兜底（Mobilerun）
         截图 + LLM 找控件，步数上限 20
         → 2.5–3.5 s/步，只在前两层失败后开
```

**升级规则**（每层失败一次就降级，最多一轮）：

| 场景 | 起点 |
|:--|:--|
| 已在能力表内（打开/关闭 app、写设置、装包、截图、按键） | L0 |
| 目标界面是原生控件（设置、系统 app、多数工具类） | L1 |
| hybrid / WebView / 游戏 / 无无障碍节点 | L2 |
| L0/L1 动作后状态未达预期 | 升 L2，并把该「任务→界面」写入能力表备注 |

## 6. 落地计划

| 阶段 | 内容 | 验收 |
|:--|:--|:--|
| **S1（本轮）** | L0 能力表 + 路由器（规则）：任务 → 命令映射，命中即执行，无模型；壳上每条命令回一行「用了 L0: xxx」 | 20 条命令全部跑通；P50 ≤ 1 s |
| **S2** | L1 封装：接 `agent-device`（已装 0.21.31）或自建 helper；prompt 只输出 `selector + 动作`，不输出坐标 | 原生界面任务步数比 L2 少 ≥40%；单步 ≤1.5 s |
| **S3** | 路由器升级为「L0→L1→L2」自动降级 + 预算（步数/秒数）+ 失败归因写进历史 | 固定任务集成功率 ≥90%，失败均有可解释原因 |
| **R2（远期）** | 机内 agent（AOSP 深改，编入 system_server/framework）→ 直调代替 ADB，才可根治 0.6 s 转发底噪 | 单步 <100 ms |
